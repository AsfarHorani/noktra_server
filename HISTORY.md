# Job Tracker Browser Extension

## What this is
A browser extension for tracking job applications, with a long-term vision of becoming an AI-powered career intelligence assistant. Phase 1 is a straightforward job application tracker (capture postings, store application data, track status). Later phases layer on AI-driven resume/job analysis, analytics dashboards, and career coaching — see "Future Phases" below.

## Status
MVP built around **automatic detection**, not manual entry. A content script scans pages the user visits for `schema.org/JobPosting` structured data, auto-creates a tracked record, and asks the user only minimal yes/no questions via a small floating widget injected on the page. The popup is a secondary dashboard for reviewing/correcting records and a manual-entry fallback for jobs the detector misses.

## MVP Scope Decisions
- **Target browser:** Chrome only, Manifest V3. (Edge/Brave should work unmodified since they're Chromium-based; not explicitly tested.)
- **Storage:** ~~`chrome.storage.local` only — no backend, no sync.~~ **No longer true as of the "Real Backend" section below** — applications/profile/settings now live in the Django server's SQLite database behind real signup/login, and the extension requires that server running (and the user logged in) to do anything. `chrome.storage.local` now holds exactly one thing: the session's auth token. This was the original MVP decision and is kept here, struck through, so the history/reasoning isn't lost — see "Real Backend: Accounts, Applications & Profile Storage" for the current state and why it changed.
- **Detection method:** Generic `schema.org/JobPosting` JSON-LD parsing first, then site-specific DOM fallbacks for sites confirmed to expose no structured data at all (Indeed, LinkedIn, d.vinci — see below), then a generic best-effort fallback (page `<title>`/`og:title` parsing) as a last resort so unrecognized sites still get *something* tracked rather than nothing. Site-specific fallbacks are more accurate where they exist; the generic one trades accuracy for coverage.
- **Prompt UI:** A shadow-DOM widget injected into the page (bottom-right corner), not the popup or a toolbar badge. Keeps interruption minimal and contextual to the job page itself.
- **Tracking is opt-in, not passive:** detecting a job on a page never persists anything by itself. A record is only created when the user clicks Save on the widget's "Track this application?" prompt, or clicks something that looks like an Apply button on the page (see "How auto-detection + prompting works" below). An earlier version auto-created a `Pending` record the instant a job was detected, silently, on every view — this over-tracked (e.g. every result in a search list got a record just from being scanned) and was changed to require an explicit action.
- **Status re-prompt trigger:** On revisiting the same job's page — no periodic/background polling. If the user never revisits, no re-prompt happens (accepted MVP limitation).
- **UI stack:** Plain HTML/CSS/JS, ES modules, no build step, no framework.
- **Auto-detect is itself opt-out, not just tracking.** A popup toggle ("Auto-detect jobs on pages", `chrome.storage.local` key `settings`, default on) lets the user turn off the widget entirely — with it off, `content/detect.js` still runs detection in the background (so the popup can ask "what's on this page?" on demand) but never shows a widget or auto-creates a record. See step 9 below.

## How auto-detection + prompting works
1. `content/detect.js` runs on every `http(s)` page (`document_idle`), extracts `JobPosting` JSON-LD (retries for a few seconds in case it's injected late by client-side JS), then falls back through `extractLinkedInFallback()` → `extractIndeedFallback()` → `extractDvinciFallback()` → `extractGenericFallback()` (see below) until one produces a job title, and bails silently if nothing is found — cheap no-op on non-job pages. Before any fallback runs, `detectJob()` also bails on a small `NON_JOB_HOSTS` denylist (meeting tools: `teams.microsoft.com`, `meet.google.com`, `zoom.us`, `webex.com`, `gotomeeting.com`) and, for `linkedin.*` hosts specifically, on any pathname outside `/jobs/` — both added after the generic fallback was observed misreading a Teams meeting-launch title and a LinkedIn profile page's `"{Name} | LinkedIn"` title as job postings. A third gate, `LISTING_PATH_SEGMENTS` (`"/search"`, `"/results"`), skips search/results-listing pages, which list many jobs, not one — added after a search-results page (`jobs.fraunhofer.de/search/?q=...`) got its own listing title read as a job and, worse, kept surfacing as an "Any update on this application?" prompt because `jobKey` collapsed every job on that page into one shared record. Whatever a fallback *does* produce is then checked against `NEGATIVE_KEYWORDS` (`"join meeting"`, `"calendar invite"`, etc.) as a fourth, host-independent safety net; a match discards the result. All of these lists live in `content/keywords.js` (see "Generic fallback" and "Structure" below), not inline in `detect.js`.
2. A `jobKey` is computed (`hostname:identifier`, falling back to `hostname+pathname`) to dedupe the same posting across revisits.
3. `scan()` keeps the detection result in module state as `currentDetection` (`{ jobKey, jobData, source }`) regardless of whether it's tracked, and looks up any existing record by `jobKey` into `currentRecord`. `source` is `"jsonld"` for real schema.org structured data or `"fallback"` for anything guessed from page title/structure (Indeed/LinkedIn/d.vinci/generic — see below); it's what decides which widget step 3 shows next. If no record exists yet, **nothing is persisted** — for `"jsonld"` detections a widget is shown asking **"Track this application?"** with a single Save button (`renderTrackPrompt()`) directly; for `"fallback"` detections, `renderConfirmPrompt()` shows the guessed title/company (so the user can judge the guess for themselves) and asks **"Are you applying here?"** Yes/No first — a concrete question about intent rather than an abstract one about page classification — and only on "Yes" does it reveal the status picker and Save button (by re-rendering into `renderTrackPrompt()`). This two-step flow for fallback-derived guesses was added after false positives were confirmed live on YouTube (every video page titles itself `"{video title} - YouTube"`, matching `GENERIC_TITLE_SEPARATORS`) and Reddit — see "Generic fallback" below for the other half of that fix. `renderTrackPrompt()` includes a status dropdown (`TRACK_STATUSES` — the full status list minus `Ignored`, which stays popup-only by design, same reasoning as step 7) defaulting to `Pending`; clicking Save creates the record with whichever status is selected, not hardcoded to `Pending`, since confirming a job posting (especially after the extra Yes/No step) doesn't necessarily mean the user just found it — they may already be mid-application or further along, and forcing everything through Pending would just mean an immediate trip to the popup to fix it. Picking any status past `Pending` also stamps today's `applicationDate`, mirroring `checkApplyCompletion()`'s behavior in step 5 — a record claiming `Applied` shouldn't be left with a blank date. Dismissing (`×`) or "No" both just close the widget for this page view without persisting anything; since nothing was saved, it prompts again on the next visit — same pattern as the status-update widget in step 6. `scan()` also clears any widget left over from a *previous* page when the current page has no detection at all — without this, a widget shown on an SPA (YouTube, Reddit, ...) before navigating client-side to a non-job page would never get torn down, since that kind of in-page navigation doesn't reload the DOM.
4. A `pointerdown` listener (capture phase, so it runs before the page's own handler might navigate away) watches for clicks on elements that look like an apply button/link — matched by text against `APPLY_KEYWORDS` (English + German: "apply now", "easy apply", "jetzt bewerben", "bewerben", etc.) on a `BUTTON`/`A`/`role="button"` element. `isApplyElement()` matches multi-word keywords ("apply now", "jetzt bewerben") as a substring, but bare single-word keywords ("apply", "bewerben") only as an *exact* match of the element's entire text — substring-matching a bare word would also fire on unrelated short clickable elements like a search facet's "Apply Filters" button or a "How to Apply" in-page jump link inside the job description, silently tracking a job the user never actually clicked Apply on. This is the *other* action that creates a record: if `currentRecord` doesn't exist yet, the listener creates one (`status: "Pending"`) from `currentDetection` before continuing — a user clicking Apply is exactly as strong a signal of intent as clicking Save, so it isn't gated behind having clicked Save first. Either way, the click does **not** mark the record Applied itself — it arms a "watch" (`jobTrackerApplyWatch` in `chrome.storage.local`, not module state) recording the record id and the time. Storage rather than a JS variable is required here because Apply is often the *start* of a multi-step flow (ATS redirect, new tab, multi-page Easy Apply modal) that tears down or leaves behind the content script context that armed it. If a record already exists and isn't `Pending` (already `Applied`/`Interview`/terminal), clicking Apply again is a no-op.
5. A 1s interval (the same one driving the SPA URL-change poll below) calls `checkApplyCompletion()` on every page load while a watch is armed: it scans `document.body.innerText` for `SUCCESS_KEYWORDS` (English + German phrases like "application submitted", "your application was sent", "bewerbung gesendet" — deliberately specific multi-word phrases, since job boards routinely show unrelated text like "32 people applied" that would false-positive on a looser match). Because the watch lives in shared storage, this can fire on a completely different page or tab than the one where Apply was clicked. On a match, the record is marked `status: "Applied"` + today's `applicationDate`, the watch is cleared, and the widget pops up as a brief toast ("Tracking … as Applied ✓"). The watch expires after 30 minutes unwatched (`APPLY_WATCH_TTL_MS`) to avoid a stale click causing a mark long after the fact. Only one apply attempt is watched globally at a time — starting a new one abandons any prior unfinished watch (accepted MVP trade-off).
6. If a record already exists with `status` in `Applied`/`Interview` (see `ACTIVE_STATUSES` in `shared/constants.js`), revisiting that job's page shows a widget asking **"Any update on this application?"** with Interview/Offer/Rejected/Ghosted buttons, plus a **"Remove from list"** button that calls the content script's own inlined `deleteApplication()` directly — letting the user untrack a job from the page itself instead of opening the popup (the popup's dashboard has had a working Delete button on every record, any status, since the MVP build; this just adds the same action at the point of interaction). The `×` dismiss just closes the widget for this page view, so it asks again next visit.
7. Records in terminal states (`Offer`, `Rejected`, `Withdrawn`, `Ghosted`, `Ignored`) get no widget at all. `Ignored` is no longer reachable from the page flow (there's no more "not applying" button) — it's now purely a manual status a user can set from the popup dashboard if they want to hide a `Pending` job they're not interested in. (In practice, opt-in tracking means far fewer unwanted `Pending` records reach the popup in the first place.)
8. Known gap: there's no universal, reliable signal for "application submitted" across arbitrary sites, so `SUCCESS_KEYWORDS` text-matching is inherently best-effort — a site whose confirmation screen doesn't contain any of the listed phrases (in English or German) will never trigger the Applied mark, and the record stays `Pending` until corrected manually in the popup. Expanding the phrase list as gaps are found is expected routine maintenance.
9. **Manual mode** (auto-detect off): `scan()` still runs the full detection above and keeps `currentDetection`/`currentRecord` up to date, and still works out *what it would show* (a `reveal` closure so both modes share the same rendering code) — the difference is only in whether that appears on its own, and *what* gets built differs by mode too, not just when it's shown:
   - **Not yet tracked.** Auto mode still confirm-first-gates `"fallback"`-sourced guesses (`renderConfirmPrompt`, see "Generic fallback" below) since those appear completely unprompted and are the false-positive-prone ones. Manual mode skips that gate unconditionally and goes straight to `renderTrackPrompt()` regardless of source — clicking the hint icon already *is* the user's explicit "yes, look at this" signal, so the extra yes/no would just be friction, not a safety net.
   - **Already tracked.** Auto mode keeps the original, narrower trigger (`renderStatusUpdatePrompt` — a compact "Any update?" button row, only for an active `Applied`/`Interview` revisit; see step 7 — Pending/terminal stays silent there to avoid nagging on every single revisit). Manual mode asks about an already-tracked job *regardless* of its current status (no nagging risk — the icon only appears once per load and does nothing until clicked), and does so via `renderTrackPrompt()` too, not `renderStatusUpdatePrompt` — see next point for why that distinction matters.
   - **One form, not two different-shaped prompts.** `renderTrackPrompt(card, host, jobKey, jobData, existingRecord)` is the single form used for every manual-mode case — genuinely editable inputs for job title, company, location, URL, employment type, status, application date, and notes (the same field set as the popup's "Add Manually" tab), not a read-only title/company summary. Called without `existingRecord` it pre-fills from the page's detected `jobData` and Save calls `addApplication`; called *with* an existing record (the "already tracked" manual-mode case) it pre-fills from the record itself and Save calls `updateApplication` on it instead — one render path, one field set, either way. This replaced an earlier version where the "already tracked" manual-mode case showed the narrow `renderStatusUpdatePrompt` button row instead — user feedback was that switching between two differently-shaped widgets (a full form vs. a handful of buttons) depending on state was confusing ("just showing two popups"); a single consistent form for every manual-mode case is more predictable. `renderStatusUpdatePrompt` still exists for auto mode's active-status revisit case, unchanged and un-widened (no `Applied` button — a record reaching it is already Applied or further along, so that transition doesn't apply there).
   - Anywhere a raw scraped value (job title, company, ...) lands inside an HTML attribute (`value="..."`) rather than a text node, it goes through `escapeAttr()`, not `escapeHtml()` — `escapeHtml()`'s textContent→innerHTML roundtrip doesn't escape `"`, since quotes carry no meaning in text-node context, only inside an attribute's value. Using it for an attribute would let a crafted page title (attacker-controlled, since it comes straight from arbitrary page content) break out of the `value="..."` attribute and inject markup.
   
   In auto mode, `reveal()` runs immediately. In manual mode, `showHintIcon(reveal)` runs instead: a small round icon appears bottom-left (the opposite corner from the widget's bottom-right, so the two are never confused at a glance), shakes briefly (a CSS `@keyframes` animation, 3 short iterations, then it just sits still — attention-grabbing once, not a permanent distraction) and does nothing else until clicked; clicking it removes the icon and calls `reveal()`. The pointerdown Apply-click listener (step 4) checks `isAutoDetectEnabled()` too and, when off, neither auto-creates a `Pending` record nor arms an apply watch — in manual mode the *only* ways a record gets created or updated are clicking through the hint icon to the widget, or the popup's own manual flow (next). `isAutoDetectEnabled()` reads the same `chrome.storage.local` key (`settings`) as `popup/storage.js`'s `getSettings()`/`updateSettings()` — inlined for the usual classic-script reason, kept in sync by hand. Separately, the content script also exposes a `chrome.runtime.onMessage` listener answering `{ type: "job-tracker:getDetection" }` with the current `currentDetection` (or, if `scan()` hasn't settled yet, one immediate non-retrying `detectJob()` call rather than making the caller wait out the full multi-second retry loop) — `popup.js`'s `tryAutoFillFromActiveTab()`, run automatically whenever the popup opens with auto-detect off, queries the active tab, sends that message, and pre-fills the "Add Manually" form with whatever comes back (status defaulted to `Pending`). This is the second, independent way to get to the same place without ever noticing the hint icon — opening the popup directly always tries this regardless of whether the icon has appeared or been clicked. If a record already exists for that page's `jobKey`, it opens the existing record for editing instead of prefilling a blank form, avoiding an accidental duplicate the same way the auto-widget flow already does via `getApplicationByJobKey`. A tab with no content script (a `chrome://` page, an extension's own page, a tab still loading) just fails the message send silently — the popup stays on its default tab rather than surfacing an error for what's a routine case.
10. **Toolbar badge — a secondary, easy-to-miss signal.** Every `scan()` — in *either* mode — calls `notifyBadge(hasJob)` (`true` right after `currentDetection` is set, `false` in the `!detected` branch), which relays a `{ type: "job-tracker:badge", hasJob }` message to `background.js`. That's the one thing content scripts can't do themselves: `chrome.action` (the toolbar-icon/badge API) isn't exposed to content-script context, only to extension pages and the background service worker — hence `background.js` existing at all (this extension's first background script). `background.js` reads `sender.tab.id` (Chrome populates this automatically for messages from a content script) and sets a small blue `•` badge on that tab's toolbar icon, or clears it. This was originally meant to be manual mode's primary signal, but user feedback was that a toolbar badge is too easy to miss/not look at — the bottom-left shaking hint icon (step 9) replaced it as the primary, on-page signal; the badge is kept as a low-cost secondary cue (e.g. useful if the page's own content happens to be covering the bottom-left corner). `notifyBadge()` is fire-and-forget (a missing/not-yet-woken background script isn't worth failing the whole scan over).

### Indeed fallback
Confirmed by direct inspection (search/listing page, apply flow, post-apply confirmation) that Indeed exposes **no** `JobPosting` JSON-LD anywhere. `detectJob()` in `content/detect.js` therefore falls back to `extractIndeedFallback()` whenever the hostname contains `indeed.` and the generic JSON-LD extraction finds nothing, reading these `data-testid` attributes from the split-pane job detail view:
- Title: `jobsearch-JobInfoHeader-title`
- Company: `inlineHeader-companyName`
- Location: `inlineHeader-companyLocation` (falls back to `jobsearch-JobInfoHeader-companyLocation`)
- **Job Description**: `#jobDescriptionText` — added after a real user-reported bug: a cover letter generated for an Indeed-sourced job came out generic (no engagement with the actual posting's requirements) because `jobDescription` was permanently empty for every Indeed-tracked record. Confirmed live on a real posting that Indeed *does* render the full description text in the DOM under this id, even though it's absent from any structured data — `extractIndeedFallback()` was simply never reading it. `.innerText` (not `.textContent`) to preserve the paragraph breaks Indeed renders.

`jobKey` is derived from the `vjk` (or `jk`) URL query parameter Indeed uses to identify the selected job. This is inherently fragile — a testid rename on Indeed's end silently breaks detection until updated — but it's the only option since there's no structured data to rely on.

**A second, more general bug was found while fixing the above**: `renderTrackPrompt()`'s Save handler (the on-page widget's primary track/update form — see step 3 in "How auto-detection + prompting works") built its save payload from an explicit field list that never included `jobDescription` at all — so *any* captured description (JSON-LD's real structured description included, not just Indeed's) was silently discarded the moment a user clicked Save on the widget, even though the field was never shown for editing there by design (only the dashboard's form has a Job Description textarea, see the Assistant section). Only the separate "click Apply" auto-create path (which spreads `currentDetection.jobData` wholesale rather than rebuilding a narrow object) happened to preserve it. Fixed by having the Save handler pass `base.jobDescription` through unedited into its payload. Caught by extending `tests/detection.spec.js` to actually click Save and inspect the POSTed body (`expectedJobDescriptionSubstring` in a fixture's `.json`) — every prior version of the suite only ever read the pre-filled form fields, never exercised the Save path, so this class of bug had no coverage at all before now.

### LinkedIn fallback
Confirmed by direct inspection that LinkedIn job pages have **no** `JobPosting` JSON-LD, no `<h1>`, no `role="heading"`, and no `data-testid` attributes on the job detail pane — and unlike Indeed, its CSS classes are content-hashed (e.g. `_9c87fdd9`) and regenerate on every deploy, so there's no selector stable enough to key off of at all. `extractLinkedInFallback()` in `content/detect.js` instead relies on two structural anchors that survive redeploys:
- **Title + company**: LinkedIn consistently sets `document.title` to `"{Job Title} | {Company} | LinkedIn"`; parsed via regex.
- **Location**: recovered by walking up from the company profile link (`a[href*="/company/"]`, itself stable because it's tied to functionality, not styling) and reading the ancestor's text lines in order (company name, then title, then `"location · posted time · applicant count"`), since there's no attribute to select the location by directly.

`jobKey` is derived from the `currentJobId` query parameter (used on the split-pane search-results view) or the numeric id in a `/jobs/view/<id>/` path. If LinkedIn changes its title format or removes the company link, this silently stops working until updated — same fragility trade-off as the Indeed fallback.

LinkedIn profile pages (`/in/...`) title as `"{Name} | LinkedIn"`, which doesn't match the two-pipe `"{Title} | {Company} | LinkedIn"` regex above, but was still being misread as a job posting because `detectJob()` fell through to `extractGenericFallback()` regardless. `detectJob()` now gates on `location.pathname.startsWith("/jobs/")` for any `linkedin.*` host before running *either* LinkedIn fallback — company pages, the feed, messaging, and profile pages are never treated as job postings, independent of what their title happens to contain.

### d.vinci fallback
d.vinci is a white-label multi-tenant ATS — client career sites are hosted at `{client}.dvinci-hr.com` and the footer reads "powered by d.vinci" (confirmed on `essilorluxottica.dvinci-hr.com`, an Apollo/EssilorLuxottica careers page). Confirmed by direct inspection that it ships no `JobPosting` JSON-LD. Unlike Indeed/LinkedIn, its `<title>`/`og:title` is unreliable *across* its own multi-step apply flow: the job description page's title is the job title, but the very next step (a "choose how to apply" page reachable by clicking the page's "Bewerben" button, e.g. `.../jobs/41181/intro`) titles itself `"Auswahl der Bewerbungsart für {job title}"` ("choice of application type for..."). `extractGenericFallback()` was reading that step as its own separate, garbled job posting — and since that fallback keys `jobKey` on `hostname+pathname`, the bogus record it produced never matched the real one already tracked (as `Pending`) from the description page, since the pathnames differ (`.../werkstudent-...` vs `.../intro`). This is the concrete bug behind a user report of "applied but it didn't save": landing on the `/intro` step first (bypassing the description page, e.g. via a resumed/bookmarked link) meant no `Pending` record existed yet, and the widget that *did* show up there was easy to dismiss unread since its title reads as garbage rather than a job posting.

The fix, `extractDvinciFallback()` in `content/detect.js`, gates on `location.hostname.includes("dvinci-hr.com")` and reads two structural anchors that hold across every step of the flow (confirmed on both the description and `/intro` pages):
- **Title**: the page's first `<h1>` — always the real job title, never the step-specific page title/CTA heading (`/intro` renders a *second* `<h1>` for its own "Bewerben Sie sich in max. 90 Sekunden!" CTA, but `document.querySelector("h1")` returns the first one).
- **jobKey**: the numeric job id embedded in every step's URL (`.../jobs/<id>/<slug>`, `.../jobs/<id>/intro`, `.../jobs/<id>/apply`, ...), matched via `/\/jobs\/(\d+)/` — same id-based `jobKey` approach as Indeed/LinkedIn, so every step of one job's apply flow collapses into a single record instead of fragmenting like the generic fallback did.
- **Location**: best-effort only — read from the `<p>` immediately after the `<h1>` (format `"{employment type} in {city}"`, e.g. "befristet in Schwabach") when present. This element only renders on the description step; other steps leave it blank.
- **Company**: left blank — no reliable structural anchor was found for it (no meta tag, no consistent DOM element) across an arbitrary d.vinci tenant, since the client-name subdomain doesn't reliably match the legal employer name (e.g. `essilorluxottica.dvinci-hr.com` hosts a job branded "Apollo", posted via reseller/agency path segment `koenigsteiner`). Same accuracy trade-off as the generic fallback's company field — correctable manually in the popup.

### Generic fallback
`extractGenericFallback()` is the last resort for any site with no JSON-LD and no dedicated fallback above, so unrecognized job sites still get tracked instead of silently ignored. It reads `og:title` (falling back to `document.title`) and splits on common separators (`" | "`, `" - "`, `" at "`, etc.) — first segment as job title, last as company. This is a real accuracy trade-off: it has no way to know whether the last segment is actually the employer or just the site's own name (e.g. "CareerSite"), so the `company` field will sometimes be wrong or blank and may need manual correction in the popup. `jobKey` falls back to `hostname+pathname` since there's no site-specific identifier to key off.

**Job-context gate (`hasJobContext()`):** the separator-based title split alone was confirmed, live, to false-positive on effectively any site with punctuation in its title — every YouTube watch page titles itself `"{video title} - YouTube"`, a 100% match rate on the `" - "` separator, with the same failure mode hitting Reddit posts and other unrelated sites. Before the title split runs at all, `extractGenericFallback()` now requires actual job context: either `location.pathname` contains a job-shaped segment (`GENERIC_JOB_PATH_SEGMENTS` — `/job`, `/careers`, `/stelle`, `/karriere`, `/emploi`, `/vacature`, etc.) or `document.body.innerText` mentions job-posting language (`GENERIC_JOB_CONTEXT_KEYWORDS` — "job description", "responsibilities", "we are looking for", "stellenbeschreibung", "wir suchen", etc., English + German). Trade-off: a real posting on a career site with neither a job-shaped URL nor any of the listed phrases still won't be caught by the generic fallback — accepted, since it's strictly better than false-triggering on every non-job site with a punctuated title. This gate is *in addition to*, not instead of, the two safety nets below — it just makes the generic fallback itself much more conservative about producing a result in the first place, whereas `NON_JOB_HOSTS`/`NEGATIVE_KEYWORDS` filter after a result was already produced.

Whatever still gets through the job-context gate is treated as a `"fallback"`-sourced (not `"jsonld"`-sourced) detection — see step 3 above — so the widget asks a neutral yes/no before showing it as a confident guess, a second independent layer of defense against exactly this kind of false positive.

Because this fallback runs on *any* unrecognized host, `detectJob()` first checks a `NON_JOB_HOSTS` denylist — originally just meeting/video-call tools (`teams.microsoft.com`, `meet.google.com`, `zoom.us`, `webex.com`, `gotomeeting.com`; a Microsoft Teams meeting-launch page's title contains `" | Microsoft Teams"`, otherwise indistinguishable from a real `"{Title} | {Company}"` job title), later expanded with a curated set of high-traffic consumer sites (YouTube, Reddit, Facebook, Instagram, X/Twitter, TikTok, Netflix, Twitch, Wikipedia, Amazon, Google's own consumer properties, Stack Overflow, npm, MDN) after the job-context gate above was found to still not be enough on its own — YouTube's `"{video} - YouTube"` title format satisfies no job-context signal but was still worth an explicit fast-path given how much traffic it accounts for. This list can never be exhaustive ("every non-job site on the internet" is unbounded) — it's a cheap belt-and-suspenders layer on top of the job-context gate, which remains the actual scalable defense. **Important when adding a host**: `isNonJobHost()` matches subdomains too, and some companies host real job postings on a *subdomain of the same domain being denylisted* (Netflix's careers are at `jobs.netflix.com`, Google's at `careers.google.com`) — entries use the exact consumer-facing subdomain (`www.netflix.com`, `www.google.com`, ...) rather than the bare domain to avoid silently swallowing those. `linkedin.com` must never be added here at all — LinkedIn already has its own `/jobs/`-path gating that runs *after* this check (see below); adding it here would short-circuit that entirely rather than refine it. As a second, host-independent layer, any fallback's output (LinkedIn/Indeed/d.vinci/generic — never real JSON-LD) is also checked against a `NEGATIVE_KEYWORDS` list (`"join meeting"`, `"calendar invite"`, `"webinar registration"`, etc.) before being accepted; `detectJob()` returns `null` on a match. None of these lists is a complete fix for the underlying over-eagerness on their own — any other non-job site whose title contains one of `GENERIC_TITLE_SEPARATORS`, isn't caught by `NEGATIVE_KEYWORDS` or `NON_JOB_HOSTS`, and happens to satisfy the job-context gate above will still produce a false-positive record. Expanding `NON_JOB_HOSTS` / `NEGATIVE_KEYWORDS` as further false positives are found is expected routine maintenance, same as `SUCCESS_KEYWORDS` below.

A third gate, `LISTING_PATH_SEGMENTS` (`"/search"`, `"/results"`), checks `location.pathname` and skips the fallback chain on search/results-listing pages — pages that list many jobs, not one. Without it, e.g. `jobs.fraunhofer.de/search/?q=...` gets its own listing-page title read as a job title, and `jobKey` (which falls back to `hostname+pathname`, ignoring the query string — see `extractGenericFallback()` above) collapses *every* job on that search page into one shared record, so any past Apply click anywhere on that listing page keeps surfacing as "Any update on this application?" on every future visit to the same search path regardless of which job is actually being looked at. Applied to the Indeed/d.vinci/generic branch unconditionally; on `linkedin.*` it's only applied as a secondary check when `extractLinkedInFallback()`'s own title-regex match fails, since that regex only matches when a specific job's detail pane is actually showing (including on LinkedIn's own split-pane search view) and is already structurally safe. Trade-off: any other ATS with a similar "job selected via query param on a `/search`-like path" pattern not special-cased like LinkedIn will now get skipped outright rather than mis-tracked — accepted for now since collapsing a listing page into one bogus shared record is worse than tracking nothing.

All of these lists — `NON_JOB_HOSTS`, `NEGATIVE_KEYWORDS`, `LISTING_PATH_SEGMENTS`, `APPLY_KEYWORDS`, `SUCCESS_KEYWORDS`, `GENERIC_TITLE_SEPARATORS`, `GENERIC_JOB_PATH_SEGMENTS`, `GENERIC_JOB_CONTEXT_KEYWORDS` — live in `content/keywords.js`, not inline in `detect.js` (see "Structure" below). Tuning or debugging detection should mean editing that one file.

## Structure
- `manifest.json` — MV3 manifest, `storage` permission, popup action, a background service worker, content scripts registered for all `http(s)` pages (`content/keywords.js` loaded before `content/detect.js`).
- `background.js` — this extension's only background script. Originally added purely to relay a toolbar-icon badge (`chrome.action.setBadgeText`/`setBadgeBackgroundColor`) on the content script's behalf, since `chrome.action` isn't exposed to content-script context — see "Manual mode" in step 9 below for what it's for. Also relays opening the Dashboard (`chrome.tabs.create`, same restriction as `chrome.action`) for `content/detect.js`'s "Sign Up" button (see "Real Backend" below) — content scripts can't call `chrome.tabs.create` directly, only extension pages/the background worker can. **Also now relays every server request `content/detect.js` makes** (`job-tracker:apiFetch` — reads the token from `chrome.storage.local` itself, does the actual `fetch()`, sends `{ data }` or `{ error }` back) — content-script `fetch()` calls to `127.0.0.1:8000` were getting blocked with `TypeError: Failed to fetch`, confirmed live; see the "Working notes" entry below for the fix. Still no detection logic of its own — purely a relay for all three message types.
- `content/keywords.js` — classic script (same import/export restriction as `detect.js` below), loaded first so its top-level `const JOB_TRACKER_KEYWORDS` is in scope for `detect.js`. Holds every keyword/host/phrase list used for detection — the single place to edit when scaling coverage or fixing a false positive/negative.
- `content/detect.js` — JobPosting JSON-LD extraction, normalization, `jobKey` dedup, widget injection and prompt logic (track/save, status-update, and remove). Inlines its own copies of `getApplications`/`addApplication`/`updateApplication`/`getApplicationByJobKey`/`deleteApplication` — now authenticated `fetch()` calls to the Django server rather than `chrome.storage.local` (see "Real Backend" below) — still inlined rather than imported for the classic-script reason further down.
- `shared/constants.js` — `STATUSES` and `ACTIVE_STATUSES`, shared between the content script and the popup so status handling stays consistent.
- `popup/popup.html` — popup markup: an auth gate (login/signup, shown until a token is stored) in front of the normal "Applications" (dashboard, default tab) / "Add Manually" (fallback) views.
- `popup/popup.css` — popup styling.
- `popup/popup.js` — dashboard logic: the auth gate, list rendering/filtering, status change, delete, and the manual-add/edit form.
- `popup/storage.js` — API client module: `getApplications`, `addApplication`, `updateApplication`, `deleteApplication`, `getApplicationByJobKey`, `clearApplications`, `getSettings`/`updateSettings`, `getProfile`, plus `login`/`signup`/`logout`/`getAuthToken`/`apiFetch`. All server access should go through this module (or `apiFetch` directly for one-off calls, see `popup.js`'s Insights/cover-letter code). Imported directly by the popup; `content/detect.js` can't import it (classic script — see the note at the top of that file) and `dashboard/` can't either (TypeScript build, see "Real Backend" below) — both keep their own inlined/native-TS copy of what they need instead.

## Data Model (MVP)
Each application row: `id`, `jobKey`, `jobTitle`, `company`, `location`, `jobUrl`, `employmentType`, `status` (`Pending`/`Applied`/`Interview`/`Offer`/`Rejected`/`Withdrawn`/`Ghosted`/`Ignored`), `applicationDate`, `notes`, `coverLetter`, `createdAt`, `updatedAt`. Lives in `server/tracker/models.py`'s `Application` now (see "Real Backend" below), not a `chrome.storage.local` array — but deliberately kept just as loosely-typed as the array was (no `status` choices constraint, JSON fields left as free-form lists) so the "add a field without a migration-shaped ceremony" property of the old schemaless-array approach isn't lost. Don't pre-add unused fields now.

## Conventions
- No build tooling in the extension itself — files are loaded directly via `chrome://extensions` "Load unpacked". Keep it dependency-free unless a real need for a bundler/framework arises. (The server now has its own, separate build/dependency story — see "Real Backend" below — this convention is about the extension's `content/`/`popup/` only.)
- All server access goes through `popup/storage.js` (popup), `content/detect.js`'s inlined copy, or `dashboard/src/app/api-client.ts` (dashboard) — never a direct `fetch()` to `127.0.0.1:8000` elsewhere.
- Status list lives in `shared/constants.js` — don't hardcode status arrays elsewhere; import from there.

## Working notes
- The content script requests `http://*/*` and `https://*/*` match patterns, so Chrome will show a "read and change all your data on all websites" install warning — inherent to scanning arbitrary career sites for structured data, not scope creep.
- Icons are omitted from the manifest for now (Chrome uses a default icon); add `icons/` when branding is decided.
- Many job boards (Indeed, LinkedIn, Glassdoor, ...) load a clicked job into the current page via client-side routing (`history.pushState`) rather than a full navigation. `content/detect.js` patches `pushState`/`replaceState` and listens for `popstate` to re-scan on these in-page URL changes — a plain one-shot `document_idle` run would otherwise miss every job clicked from a search results list. In practice the patch alone wasn't reliable (confirmed on Indeed: the first job on a page load worked, but clicking a different job afterward did nothing) — likely because the page's own router had already captured a reference to the original `pushState` before our `document_idle` content script got a chance to patch it, a real race against a heavy SPA bundle. A `setInterval` poll (1s) was added as a belt-and-suspenders fallback that catches any URL change regardless of how it happened; `checkApplyCompletion()` (see "How auto-detection + prompting works") rides the same interval tick since it's a cheap no-op unless an apply watch is armed.
- **`content/detect.js` must stay a classic script with no `import`/`export`.** `"type": "module"` is not honored for entries in the manifest's static `content_scripts` list (it only applies to a different, dynamic-registration API) — declaring it there is silently ignored, so a script using static `import` fails with `Uncaught SyntaxError: Cannot use import statement outside a module` and never runs at all. Because of this, `content/detect.js` inlines its own copies of the storage helpers and `ACTIVE_STATUSES` rather than importing `popup/storage.js` / `shared/constants.js` — keep them in sync by hand if the storage schema changes. `popup/popup.html` loading `popup.js` via `<script type="module">` is unaffected; that's a different, well-supported mechanism.
- Known limitation: sites with no `JobPosting` JSON-LD, no site-specific fallback, and page metadata that doesn't follow a recognizable `"{title} {separator} {company}"` pattern will still produce a wrong or incomplete record via `extractGenericFallback()` rather than a correct one — there's no universal signal to fall back to further than that. Correctable manually in the popup.
- No automated tests yet given the small MVP surface; verify manually via "Load unpacked" in `chrome://extensions`.
- **"Uncaught (in promise) Error: Extension context invalidated"** in a job page's console is expected, not a bug: reloading/updating the extension orphans any content script already injected into tabs open at that moment, and its `chrome.*` bindings start throwing. Refreshing the affected tab fixes it (re-injects a live content script). `content/detect.js`'s `isContextInvalidated()` catches this specific error at every async entry point (scan, the apply pointerdown listener, widget button handlers, `checkApplyCompletion()`) so it fails quietly instead of surfacing as an unhandled rejection — worth remembering whenever testing via repeated "Load unpacked" reloads with job tabs already open.
- **`background.js` is an MV3 service worker, not a persistent background page** — Chrome terminates it when idle and wakes it back up on the next message, same as any MV3 extension. There's no state to lose on termination here (it holds nothing — every message is handled and forgotten), so this is a non-issue in practice, but worth knowing if the toolbar badge ever seems to lag by a beat right after Chrome/the extension has been idle a while: that's the service worker waking up, not a bug.

# Phase 2: Analysis Server

## What this is
The first slice of "Future Phases" AI: a local Django server (`server/`) that compares jobs which led to an interview/offer against jobs that were rejected/ghosted, and surfaces qualitative patterns ("you tend to hear back from mid-size manufacturing companies but not from large FinTechs") plus a few actionable recommendations. Runs entirely on the user's machine. Originally opt-in and only reached by clicking "Analyze" — **as of "Real Backend" below, the server is no longer optional**: it's required for every feature in the extension, not just this one, since it's now also where applications/profile data lives.

## Scope decisions
- **LLM runtime: Ollama**, not LM Studio or in-process `transformers`/`vllm`. Ollama's local REST API (`localhost:11434`) is trivial to call from Django with `requests`, needs no GPU for a small model, and is scriptable/headless-friendly — LM Studio's strength (GUI model management) isn't needed for a server process, and self-hosting via `transformers` is more infra than an MVP analysis feature justifies. Default model is `llama3.1:8b`, overridable via `OLLAMA_MODEL` env var (see `server/.env.example`) — swapping to `qwen2.5:7b`/`mistral`/etc. needs no code change.
- **Single provider, no abstraction layer yet.** The Future Phases doc describes a full provider interface (`summarize()`, `analyzeResume()`, etc.) spanning OpenAI/Anthropic/Gemini/Ollama/LM Studio. That's deliberately not built yet — `server/analysis/ollama_client.py` talks to Ollama directly. Generalize it into a provider abstraction when a second provider is actually needed, not before.
- **Stats are computed in Python, never asked of the LLM.** `server/analysis/stats.py` computes counts/rates deterministically; the prompt (`server/analysis/prompts.py`) hands the model pre-computed stats and two pre-grouped lists (positive: Interview/Offer, negative: Rejected/Ghosted) and explicitly tells it not to invent numbers — it only describes qualitative differences between the groups. This follows the Future Phases guiding principle that "AI analysis should be explainable and based on evidence from the user's application history"; LLMs are unreliable at exact counting, so counting isn't delegated to one.
- ~~**Server is stateless — no models, no DB, no migrations.**~~ **No longer true** — see "Real Backend" below. This view itself still doesn't touch a model directly (the applications array is passed in the request body, same as always, computed fresh each call, nothing analysis-specific persisted) but the server as a whole now has models/migrations/a database, and this endpoint requires the caller to be logged in like every other one.
- **CORS via `host_permissions`, not `django-cors-headers`.** `manifest.json` declares `host_permissions` for `http://127.0.0.1:8000/*` and `http://localhost:8000/*`, which exempts fetches from extension pages (the popup) from CORS enforcement entirely. This avoids adding a CORS-handling dependency to the Django side.
- The `/api/analyze/` view is `@csrf_exempt`: it's a JSON API called by `fetch` from the extension popup, not a Django-rendered form, so there's no session/cookie to protect against forgery of. (Authentication is handled separately, via the `Authorization: Token ...` header — see "Real Backend" below — which is a different concern from CSRF.)

## Structure
- `server/manage.py`, `server/jobtracker_server/` — standard Django project (`settings.py` reads `OLLAMA_URL`/`OLLAMA_MODEL` from env, defaults documented in `server/.env.example`).
- `server/analysis/views.py` — the one endpoint, `POST /api/analyze/`.
- `server/analysis/stats.py` — deterministic counts/rates (`compute_stats`).
- `server/analysis/prompts.py` — builds the qualitative-comparison prompt (`build_prompt`); groups by outcome, truncates notes, hedges explicitly when the decided-applications sample is under 3. Actual prompt wording lives in `server/analysis/prompts.json`, loaded once at import time — see the "Prompts are externalized to JSON" note under Assistant's Structure section below for why and for the pattern both this file and `assistant/prompts.py` follow.
- `server/analysis/ollama_client.py` — thin wrapper over Ollama's `/api/generate` (`format: "json"`); on a connection error or non-JSON model output, fails soft (503 with a clear message, or a fallback `insights` object) rather than crashing the request.

## Working notes
- Run with `server/.venv` (a local venv — see `server/requirements.txt`); start via `python manage.py runserver 8000`, and separately have Ollama running (`ollama serve` + `ollama pull llama3.1:8b` or whichever model `OLLAMA_MODEL` points at).
- If the Django server or Ollama isn't running, the popup's Insights tab shows an inline error instead of failing silently — see the `catch` block in `popup/popup.js`'s analyze-button handler.
- Unlike the extension (no build tooling, so no test runner), the server is plain Django with `manage.py test` available for free. `server/analysis/tests.py` covers `compute_stats()` directly and the view's request-handling paths (malformed JSON, missing key, empty list, success, Ollama-unavailable, missing-auth) via Django's test client — the Ollama call is mocked (`unittest.mock.patch` on `analysis.views.ollama_client.generate`) so the suite runs in well under a second with no live Ollama/GPU needed. Run the whole server suite (all five apps) with `.venv/bin/python.exe manage.py test`.
- `server/test_payloads/*.json` are hand-crafted fixtures for *manual* end-to-end testing against a real running Ollama (verifying actual LLM output quality, which the mocked unit tests intentionally don't check): `mixed.json` (realistic mix meant to produce a real interview/rejection pattern), `small_sample.json` (exercises the low-sample hedge note in `prompts.py`), `all_rejected.json` (zero positive-signal jobs), `empty.json`. Feed one to a running server — now needs a `-Headers @{ Authorization = "Token <key>" }` too, since `/api/analyze/` is `require_auth`'d like everything else (see "Real Backend" below); get a token via `POST /api/auth/signup/` or `/login/` first, e.g. `Invoke-RestMethod -Uri http://127.0.0.1:8000/api/analyze/ -Method Post -ContentType "application/json" -Headers @{ Authorization = "Token <key>" } -Body (Get-Content server/test_payloads/mixed.json -Raw)`.

# Real Backend: Accounts, Applications & Profile Storage

## What this is
A full reversal of the original "storage: `chrome.storage.local` only, zero required network dependency" MVP decision (see the struck-through bullet under "MVP Scope Decisions" above): applications, the candidate profile, and settings now live in the Django server's SQLite database, scoped per user behind real signup/login. The extension is no longer usable offline or without the server running — every feature, not just the AI ones, now needs `python manage.py runserver` up and the user logged in.

**Why:** explicit user request — dissatisfaction with `chrome.storage.local`-based state during a debugging session (a coordinate-scaling mismatch in browser-automation tooling was initially mistaken for an app bug) led to wanting a real backend instead. MySQL was the original target; dropped after a local `root` password reset couldn't be completed on the dev machine (see the plan file this was built from, `mutable-coalescing-kettle.md`, for the full back-and-forth) — SQLite instead, which needed no new service, no credentials, and no new dependency, since Django's ORM doesn't care which database engine it's talking to.

## Scope decisions
- **Real signup/login, not a single shared password.** `django.contrib.auth`'s built-in `User` model, `username` set to the user's email (no separate username field exposed anywhere). Django's built-in password hashing (PBKDF2) and the `AUTH_PASSWORD_VALIDATORS` already sitting in `settings.py` since the project's initial `startproject` scaffold (unused until now) do the actual validation/hashing work — nothing hand-rolled there.
- **Hand-rolled token auth, not Django REST Framework.** This project has stayed deliberately dependency-light throughout (`requirements.txt` was, and still is, just `Django` + `requests` — this feature added no new dependency at all). A single `AuthToken` model (`server/accounts/models.py` — `user` FK, random 64-char `key`, `created_at`) plus one `require_auth` decorator (`server/accounts/auth.py`) that reads an `Authorization: Token <key>` header and sets `request.user` covers everything actually needed, in the same plain-Django-view style (`JsonResponse`, `@csrf_exempt`, a `_parse_body` helper) every other endpoint in this project already uses. Pulling in all of DRF for this would have been the first real framework-within-a-framework here.
- **SQLite, not MySQL** (see "Why" above) — `server/db.sqlite3` was already there (holding only `django.contrib.admin`/`auth`/`sessions`' own tables) and is now the real data store. No separate DB service to install, run, or credential for a single-machine personal tool.
- **Client-facing JSON keeps its camelCase shape** (`jobTitle`, `applicationDate`, `coverLetter`, ...) even though the DB columns are Django-conventional snake_case (`job_title`, `application_date`, `cover_letter`, ...) — `server/tracker/serializers.py`'s plain dict-shaping functions (`application_to_json`/`apply_application_fields`, and the `Profile`/`UserSettings` equivalents) translate at the API boundary. This kept the diff in every JS/TS call site to "swap the storage call for a fetch," not "rename every field access across three client contexts."
- **`analysis`/`assistant` endpoints kept their existing request/response shapes** — the client still sends full `profile`/`application` objects in the body for cover-letter/answer generation, rather than an ID the server looks up itself. Just gained `@require_auth`. Refactoring to pull `Profile`/`Application` from the DB by ID instead is a reasonable future cleanup (it would shrink the request payloads), but wasn't needed to satisfy what was actually asked for here.
- **`Application.status`/`application_date` stay plain `CharField`s, no `choices=`/`DateField` constraint**, and `Profile`'s `experience`/`education`/`projects`/`skills`/`languages`/`certifications`/`interests` are `JSONField`s holding whatever shape the client sends — deliberately as loosely-typed as the `chrome.storage.local` array it replaces, so a client-side schema change (a new profile field, say) still doesn't need a migration. See the Data Model section above.
- **The auth token is the one thing still in `chrome.storage.local`** (key `authToken`) across all three client contexts (popup, dashboard, content script) — it has to live somewhere the extension can read it locally to attach to requests, same as any client-side app's session token/cookie.

## Structure
- `server/SCHEMA.md` — the ER diagram (Mermaid) for every model below and how they relate to `auth.User` — maintained by hand, update it if `accounts/models.py`/`tracker/models.py` change.
- `server/accounts/` — `models.py` (`AuthToken`), `views.py` (`POST /api/auth/{signup,login,logout}/`), `auth.py` (`require_auth`, imported by every other app's views), `tests.py`.
- `server/tracker/` — `models.py` (`Application`, `Profile`, `UserSettings` — one/one/one-per-user respectively), `serializers.py` (the camelCase↔snake_case dict-shaping functions), `views.py` (`GET/POST /api/applications/`, `GET/PATCH/DELETE /api/applications/<id>/`, `GET /api/applications/by-key/?jobKey=...`, `DELETE /api/applications/clear/`, `GET/PUT /api/profile/`, `GET/PUT /api/settings/` — all `require_auth`'d and scoped to `request.user`), `tests.py` (CRUD plus explicit per-user ownership-isolation tests — user A can't read/edit/delete user B's rows).
- `popup/storage.js`'s `apiFetch`/`getAuthToken`/`clearAuthToken`/`login`/`logout` — the popup's API client (`login` but deliberately no `signup`, see below); every other function in that file (`getApplications`, `addApplication`, ...) is now a thin `apiFetch` call instead of a `chrome.storage.local` call, same names/signatures as before so `popup.js`'s call sites barely changed.
- `dashboard/src/app/api-client.ts` — the dashboard's equivalent `apiFetch`, used by `applications-service.ts`, `profile-service.ts`, `auth-service.ts`, and `assistant-api.ts`. `Application.id`/`Profile` fields changed from client-generated string IDs to server-assigned numeric ones (Django's `BigAutoField`) — `generateId()` is gone from both `popup/storage.js` and `applications-service.ts`, the server assigns IDs now.
- `content/detect.js`'s inlined `getApplications`/`addApplication`/`updateApplication`/`getApplicationByJobKey`/`deleteApplication`/`isAutoDetectEnabled`/`login` — `getAuthToken()` still reads `chrome.storage.local` directly (plain storage access, no CORS concern), but `apiFetch()` itself no longer calls `fetch()` in the content script at all — see the `job-tracker:apiFetch` bullet under `background.js`'s entry above; this was a real bug, not a style preference, see the "Working notes" entry below. When `scan()` detects a job but finds no stored token, it shows the same non-intrusive hint icon manual mode already used (bottom-left, regardless of the auto-detect setting) but with a distinct 🔒 icon and tooltip instead of the usual 💼 — the icon itself signals *why* it's there before it's even clicked. Clicking it reveals a real choice (`renderLoginOrSignupPrompt`: Log In vs. Sign Up), not an immediate redirect — see below.
- **Sign-up always goes to the Dashboard; logging in can happen right where you are.** Every not-logged-in surface — the popup's `#auth-gate`, and `content/detect.js`'s 🔒 hint icon — presents a real choice, not an immediate redirect: a "Log In" option that reveals an actual email/password form in place, and a "Sign Up" option that opens the Dashboard (`dashboard/src/app/app.html`'s `@if (auth.isLoggedIn() === false)` block, the one place with a real signup form). The asymmetry is deliberate: creating a new account has more steps/validation than the Dashboard's fuller layout is a better fit for, but typing an email/password you *already have* shouldn't require leaving the page or popup just to reach a form that does the same thing. Concretely: `popup/storage.js` and `content/detect.js`'s inlined API client both got a `login()` (POST `/auth/login/`, store the token) but deliberately no `signup()` — `popup/popup.js`'s `#login-form` and `content/detect.js`'s `renderInlineLoginForm()` are the two inline forms; both `openDashboardAuthButton`-style buttons still just do `chrome.tabs.create`/`openDashboard()` for signup. The Dashboard's `auth-service.ts`, the popup's `storage.js`, and `content/detect.js` all read/write the *same* `chrome.storage.local` `authToken` key, so logging in anywhere carries over everywhere else automatically (the popup picks it up next time it's opened, since popups are destroyed/recreated on each open in Chrome).
- **Both `logout()` implementations (`popup/storage.js`, `dashboard/src/app/auth-service.ts`) had a real bug, found while verifying this**: `try { await apiFetch(...) } finally { clearAuthToken() }` with no `catch` still re-throws after `finally` runs — so a failed server-side logout call (server not running, network issue) would propagate out as an unhandled rejection, past the point the comment already claimed was handled ("clear locally regardless of whether the server call succeeded"). In the popup this left the UI stuck showing the now-invalid app shell instead of returning to the login screen, since `popup.js`'s click handler (`await logout(); showAuthGate();`) never reached its second line. Fixed by adding an explicit `catch {}` in both — confirmed live (a mocked failing logout call) that the popup now correctly returns to the auth gate either way.
- **The Dashboard's signup form has a Confirm Password field**, checked client-side in `app.ts`'s `submitAuthForm()` (`password !== confirmPassword` → an inline error, no server call at all — the server only ever sees one password and has no opinion on this) — a plain typo-catcher, not a security control. The `#authConfirmPassword` input has to stay physically in the DOM in login mode too, not behind an `@if`: a template ref (`#ref`) declared inside an `@if` block is scoped to that block, and the surrounding `<form>`'s `(submit)` handler needs to read `authConfirmPassword.value` regardless of mode. It's hidden via `[class.hidden]` instead, and only actually `required` in signup mode (`[attr.required]`). Two real bugs turned up getting this right, both worth remembering: (1) `app.css` had no `.hidden` utility class at all — every other conditional bit of this template uses `@if`/`@switch`, never class-toggling, so this was the first thing in the whole dashboard that needed one; (2) the first attempt at adding one (`display: none`, no `!important`) still lost to `.field-label`'s `display: block`, since both are single-class selectors and `.field-label` happens to be declared later in the file — same fix `popup.css`'s `.hidden` already uses (`!important`) for the exact same reason, applied here too. Confirmed live: hidden in login mode, shown in signup mode, mismatched passwords blocked before any network call, matching passwords sign up successfully.

## Working notes
- **Every existing test file that hit an endpoint needed an auth token added** — `analysis/tests.py`'s `AnalyzeViewTests` and all three classes in `assistant/tests.py` now create a `User`/`AuthToken` in `setUp()` and attach `HTTP_AUTHORIZATION` on every request; each also gained a `test_missing_auth_returns_401`-style test. This is the expected shape for any *future* endpoint's tests too, not a one-off migration artifact — copy the pattern from `accounts/tests.py`/`tracker/tests.py` rather than mocking auth away.
- `server/jobtracker_server/settings.py`'s `DATABASES` comment was updated in place (it used to say "unused by this project's own code... chrome.storage.local remains the sole source of truth" — no longer true) rather than left stale.
- Known gap, accepted for now: no password-reset flow, no email verification, no rate-limiting on login attempts. This is a personal local tool, not a public-facing service — revisit if that ever changes.
- Migrations: `accounts.0001_initial` and `tracker.0001_initial` are the two new migration files; run `python manage.py migrate` after pulling this change (a fresh `db.sqlite3` needs it too — the file existed before but only for `contrib.auth`'s own tables, which is a separate migration path already run via the initial `startproject` scaffold).
- **Content-script `fetch()` calls to `127.0.0.1:8000` are not exempt from CORS the way extension-page fetches are — confirmed live, not theoretical.** The original assumption (stated in this doc's own Phase 2 section: `host_permissions` "exempts fetches from extension pages... from CORS enforcement entirely") is true for the popup and the Dashboard, but a real user-reported bug — the on-page widget silently failing with `TypeError: Failed to fetch` on a real job page (`de.indeed.com`), while the exact same request worked fine from the popup — showed it does *not* extend to a content script's own `fetch()`, which runs closer to the *page's* origin (`de.indeed.com`) than the extension's for this specific purpose, even though content scripts are otherwise treated as part of the extension for most permission checks. The fix: `content/detect.js`'s `apiFetch()` no longer calls `fetch()` at all — it sends a `job-tracker:apiFetch` message to `background.js` (an unambiguous extension page, where the bypass reliably works) and lets that make the actual request. `getAuthToken()` was unaffected and still reads `chrome.storage.local` directly in the content script — that's a storage API, not a network one, and was never CORS-restricted in the first place. Confirmed the fix doesn't regress detection: the Playwright suite's route interception (`context.route("**/*", ...)` in `detection.spec.js`) still catches requests originating from the background service worker the same way it caught the old content-script-originated ones, so all 16 fixtures still pass unchanged.
- **A stale/orphaned content script can look like a real bug and isn't one.** Reloading the extension (`chrome://extensions`'s refresh icon) after a code change orphans the content script in any tab that was already open before the reload — its `chrome.*` bindings start throwing `Uncaught Error: Extension context invalidated` (see the "Working notes" entry on this in the base extension section above; `isContextInvalidated()` is supposed to catch this at every entry point, but a raw `fetch()` call — as opposed to a `chrome.*` API call — can also throw this same error text on a torn-down context, and isn't currently one of the guarded call sites, since it didn't need to be before this change moved `apiFetch()` off `fetch()` entirely). The fix is always the same: refresh the tab, not the extension code. When debugging a "nothing shows up" report, check `chrome://extensions`'s Errors panel for *when* an error happened relative to the last reload before assuming it's a fresh bug.

# Cross-site detection tests (Playwright)

## What this is
Automated regression coverage for `content/detect.js`'s detection logic across ~16 real job sites, loading the *actual* unpacked extension (not a reimplementation of the logic) via Playwright. Lives in `tests/`, separate from `server/`'s Django tests and the (currently untested) `dashboard/` Angular app.

## Scope decisions
- **Playwright, loading the real extension** — `tests/extension-fixtures.js` uses `chromium.launchPersistentContext` with `--load-extension=<repo root>` (the documented Playwright pattern for MV3 extension testing). A passing test means the actual shipped `content/detect.js` produced the right widget on a real page, not that a parallel copy of its logic agrees with itself. `headless: false` is required — MV3 background service workers don't reliably load under classic headless Chromium; a CI runner needs a virtual display (e.g. `xvfb-run`).
- **Fixtures, not live sites, as what tests run against day-to-day.** Real job boards have bot detection, logins, and DOM drift that would make live tests flaky and untrustworthy. `tests/fixtures/<name>.html` + `<name>.json` (recording the source `url`, `expectDetected`, and optionally `expectedJobTitle`/`expectedCompany`) are frozen snapshots. `tests/detection.spec.js` is fully data-driven off whatever `.json` files exist — adding site #17 means dropping in an html/json pair, not writing new test code. **Never automated against LinkedIn on an ongoing basis** — its ToS prohibits scripted access; the one LinkedIn fixture here was captured via a single manual, interactive-browser visit (not a script), and the test suite only ever replays that saved snapshot afterward, never re-hits linkedin.com.
- **Fixtures are served via request interception, not a local static file server.** This was a real design bug caught while building this: `detectJob()`'s host-gated logic (`extractIndeedFallback`, `extractLinkedInFallback`, `extractDvinciFallback`, `NON_JOB_HOSTS`, `LISTING_PATH_SEGMENTS`, LinkedIn's `/jobs/` path check) all read `location.hostname`/`location.pathname` — serving fixtures from `127.0.0.1` would make every one of those checks see the wrong host and silently behave as if on an unrecognized site, regardless of the HTML content. Each test instead calls `context.route("**/*", ...)`, navigates to the fixture's *real* recorded URL, and fulfills that exact request with the saved local HTML — `location.href` is genuinely correct because that's really what was navigated to, even though nothing left the machine. Any other request (subresources the page's own JS tries to fetch) is aborted; detection only ever reads what's already in the DOM/JSON-LD at `document_idle`, so fixtures captured post-render (see below) don't need their subresources to actually succeed.
- **Two capture methods, picked per site based on what actually worked**: `tests/capture-fixture.js` (a one-off dev utility, not part of the suite) launches a normal headless Chromium and saves `page.content()` straight to disk — used for JS-rendered sites (Greenhouse, SmartRecruiters) where a plain `curl` gets pre-hydration placeholder content. Plain `curl` was used first for server-rendered pages (faster, and confirms what a simple GET actually returns before reaching for a browser). Where a site actively blocks automation (**Indeed**: real page returns a Cloudflare challenge to headless requests; **LinkedIn**: real page is 200-300KB and its *logged-out* title format doesn't even match `extractLinkedInFallback()`'s regex — only the logged-in one does, a real finding, not just an obstacle), the fixture is a hand-built minimal HTML file using selector names and text values confirmed live via an interactive browser session — documented as such in a comment at the top of each such fixture, not presented as a full page capture.
- **Auth is seeded, not exercised.** Every widget/status prompt is now gated on a logged-in session (see "Real Backend" below) — without a token, `content/detect.js` shows a "log in via the popup" hint instead of the track prompt these tests actually assert on, which broke all 9 `expectDetected: true` fixtures the first time this ran post-migration. `extension-fixtures.js`'s `seedAuthToken()` writes a fake token straight into `chrome.storage.local` via the extension's background service worker (`context.serviceWorkers()`) before each test — a plain web page (or `page.addInitScript`) can't reach `chrome.storage` at all, only an extension context can, and the service worker shares the same storage area content scripts read from. `detection.spec.js`'s route handler also mocks the two authenticated calls `scan()` now makes (`/api/applications/by-key/` → always `null`, i.e. "never tracked before"; `/api/settings/` → `{autoDetect: true}`) rather than requiring a real Django server to be running for a fixture suite that's about detection logic, not auth.

## Fixture inventory (by category)
- **`positive-jsonld`**: real `schema.org/JobPosting` data — `schwarz-digits-jsonld`, `lever-palantir-jsonld`, `dvinci-description-jsonld` (a real finding: this d.vinci tenant now ships JSON-LD on its description page, unlike the `essilorluxottica` tenant CLAUDE.md's earlier d.vinci investigation was based on — tenant-dependent, apparently).
- **`positive-generic-fallback`**: `greenhouse-anthropic-generic`, `smartrecruiters-servicenow-generic` (both turned out to exercise the "`og:title` has no separator, use it whole" path rather than the actual split — a real finding caught by running the suite, not assumed going in), `small-company-generic-split` (hand-built specifically to cover the actual `GENERIC_TITLE_SEPARATORS` split path, since neither real capture ended up doing so).
- **`positive-{indeed,linkedin,dvinci}-fallback`**: `indeed-fallback`, `linkedin-fallback`, `dvinci-intro` (the exact documented garbled-`/intro`-title regression case).
- **Negative / regression guards**: `youtube-negative`, `reddit-negative` (the sites that motivated the false-positive fixes earlier this session), `wikipedia-negative`, `amazon-negative` (other `NON_JOB_HOSTS` entries), `linkedin-profile-negative` (the `/jobs/` path gate), `fraunhofer-listing-negative` (`LISTING_PATH_SEGMENTS`, the exact real example CLAUDE.md's writeup documents), `jetbrains-negative` (a site that was never in any denylist — passes naturally because its title has no separator match; the real page investigated for an earlier user report).

## Verification / how to run
```
cd tests
npm install
npx playwright install chromium   # separate browser binary from the user's regular Chrome
npx playwright test               # full suite
npx playwright test -g "<name>"   # one fixture, for debugging
```
All 16 pass as of when this was written. To add a new site: capture with `curl`/`node capture-fixture.js <url> <name>` (try `curl` first, it's free), write a matching `<name>.json`, run the suite — no other changes needed.

# Dashboard (Angular)

## What this is
A roomier, dedicated view for reviewing the job search, opened from a "Dashboard ↗" button in the popup header — laid out as a left sidebar (Overview/Jobs/Profile, icon + label, active-state highlighting, a live count badge on Jobs) with the selected page's content to the right, rather than one long scrolling page. Overview has the stats flow diagram (counts per status); Jobs has full CRUD (add/edit/delete/**clear all**) over tracked applications plus the cover-letter/interview-answer generation panels; Profile has the resume upload/candidate-profile editor (see "Assistant" below). Reads/writes the exact same `chrome.storage.local` keys as the popup (`applications`, plus its own `profile`) — no separate data store for the CRUD/stats parts, no backend involvement, no LLM outside the Assistant feature.

## Scope decisions
- **Modern Angular, not AngularJS.** AngularJS (1.x) has been unmaintained/unpatched since Dec 2021; modern Angular is current and secure. This is a deliberate, scoped exception to the rest of the project's "no build tooling" rule — `content/` and `popup/` remain plain script tags with zero build step; only `dashboard/` has one (Angular CLI/TypeScript/npm).
- **Lives inside the extension, not a standalone app.** A new full-tab page (`dashboard/dist/browser/index.html`, opened via `chrome.tabs.create` from the popup). Originally read `chrome.storage.local` directly like the popup did — **as of "Real Backend" above, both now talk to the Django server instead** via `api-client.ts`'s `apiFetch`, `chrome.storage.local` reduced to just the `authToken` key.
- **Storage logic is native TypeScript here, not imported from `popup/storage.js`.** Originally it *was* a direct import (Angular being a real ES module/TypeScript build meant no classic-script restriction like `content/detect.js` has) — but `dashboard/tsconfig.app.json` has `allowJs: false`, which excludes raw `.js` files from the TypeScript program entirely, so that import stopped compiling. `applications-service.ts` now has its own native-TS copy of the same server CRUD calls (same behavior, `fetch()` instead of `chrome.storage.local` now) — the same kind of "can't import across this boundary, so duplicate deliberately" situation `content/detect.js` already established, just for a config reason here instead of a classic-script one. `dashboard/src/app/constants.ts` is the same story for `shared/constants.js`'s `STATUSES`. `clearApplications()` lives here as `ApplicationsService.clearAll()` (calling `DELETE /api/applications/clear/`) rather than in `popup/storage.js`, since nothing outside the dashboard needs it.
- **`baseHref: "./"`** is set in `dashboard/angular.json`'s build options (confirmed in the built `index.html`'s `<base href="./">`) — required because the built page is served from `chrome-extension://<id>/dashboard/dist/browser/...`, not from a domain root; the CLI's default absolute `/` base href would break every asset reference.
- **Build output path**: `angular.json`'s `outputPath: "dist"` makes the build land at `dashboard/dist/browser/` (not the CLI's nested default `dist/dashboard/browser/`) — this is the exact path `popup.js`'s `chrome.runtime.getURL(...)` call points at.
- **Stats flow diagram, no charting library.** `stats-flow.ts` tallies a plain count per status client-side (no rate/denominator math — that nuance is specific to `server/analysis/stats.py`'s interview/offer rates, not needed here) and renders it as plain inline SVG-free HTML/CSS bars — no D3/ngx-charts for what's fundamentally 8 numbers. Colors follow the `dataviz` skill's method: `Pending`/`Applied`/`Interview` are an **ordinal** ramp (one hue, monotone lightness — ordered progress, not yet judged), `Offer`/`Rejected`/`Ghosted` use **status** colors (a real good/serious/critical judgment applies), and `Withdrawn`/`Ignored` use plain neutral ink (a user-driven closure, not a judged outcome) — all hex values are that skill's documented, pre-validated steps, not eyeballed.
- **Forms are uncontrolled** (template-ref reads on submit, `[value]` one-way bindings for pre-fill), not `[(ngModel)]` two-way binding — this build has no `zone.js` dependency (confirmed: not in `package.json`, no `polyfills.ts` generated), so this sidesteps any question of whether two-way binding reliably repaints under zoneless change detection, and mirrors the pattern `popup.js` already uses (`getElementById(...).value` on submit).
- **Sidebar navigation, not one long scrolling page.** `App`'s `activePage` signal (`'overview' | 'jobs' | 'profile'`) picks which page's content renders via `@switch` — added after user feedback that the original single-scroll layout (stats, then profile, then applications, all stacked) felt "vague and boring." Icons are small hand-written inline SVGs (a 3-icon set doesn't justify an icon-library dependency), not emoji — chosen for a more consistent, deliberate look than emoji render inconsistently across platforms. Colors reuse the same page-plane/surface/ink token roles `stats-flow.ts` already established from the `dataviz` skill's reference palette, so the new page chrome and the existing stats diagram read as one system instead of two different color schemes.
- **Vibrant redesign + Kanban board, competing directly with Huntr's UI.** User feedback: the dashboard "looks very boring" next to Huntr, and asked for "cool colors and features." Two changes, done together:
  1. **A violet/indigo brand accent (`--accent: #7c3aed`, `--accent-gradient`) replaces the old flat blue throughout** — sidebar (gradient brand mark, gradient active-nav pill), buttons, focus rings, the Jobs page's view toggle, stat-tile top accents. Per-status colors are deliberately **untouched** — still `constants.ts`'s `STATUS_COLORS` (see below), the same `dataviz`-skill-validated palette `stats-flow.ts` always used — since those encode real meaning (which the redesign doesn't get to recolor on a whim) and only the chrome *around* the data got more vibrant, not the data encoding itself.
  2. **A Kanban board (`dashboard/src/app/application-board/`) is now the default Jobs-page view**, with the existing table kept as a "List" toggle alongside it (`app.ts`'s `jobsView` signal). One column per status (`STATUSES`), colored via the same `STATUS_COLORS`; drag a card to a different column to change its status (`@angular/cdk`'s `DragDropModule` — a new dependency, added specifically for this, same "the dashboard has its own build/dependency story" precedent as `pdfjs-dist`/`mammoth`). Card moves are applied optimistically to a local `workingApplications` signal (re-synced from the real `applications()` input via `effect()`) so a drag lands in its new column immediately instead of snapping back for the length of the update-then-reload round trip in `ApplicationsService`.
- **`constants.ts` gained `STATUS_COLORS`** — the same eight hex values `stats-flow.ts` always hardcoded in its own `ROW_ORDER`, pulled out into one shared map so a status is the same color everywhere in the dashboard (stats bars, board columns/cards, list status pills), not just in the one place that happened to define it first. `stats-flow.ts` now imports it instead of owning its own copy.
- **A real, pre-existing bug was found (and fixed) while visually verifying this redesign, unrelated to the color changes themselves**: `application-list.html`'s status `<select>` used `[value]="app.status"` bound on the `<select>` element itself (no `ngModel`/reactive forms in this uncontrolled-forms codebase — see the bullet above) — every dropdown *always* displayed "Pending" regardless of the record's actual status, confirmed live via a populated preview build (the newly-added colored left-border/pill background, driven by the same `app.status` through a separate `statusColor()` binding, rendered correctly the whole time, which is what made the mismatch visually obvious — a plain "Applied" row with a blue-tinted pill still literally read "Pending"). Root cause: a raw DOM property set on a native `<select>` outside Angular's forms module doesn't reliably re-select the matching `<option>` once a row's data arrives asynchronously (a known Angular/native-`<select>` timing quirk). Fixed by moving the binding onto each `<option>` instead (`[selected]="s === app.status"`), the standard reliable pattern for this outside `ngModel`/`formControl`. This bug likely predated the redesign entirely (the original binding shape was untouched by earlier sessions) — worth remembering that a color/style pass over an existing view is also a good forcing function for actually looking at whether that view was already correct.
- **Verification technique for changes that need real data, not just a clean build**: `chrome.storage`/`fetch` being unavailable outside the extension (see the Working notes entry below) is normally an accepted verification gap — but confirming multi-status color mapping, the board's drag-and-drop, or the exact select bug above needed to actually *see* several differently-statused records rendered, not just "zero console errors." The technique: a temporary, uncommitted `dist/browser/preview.html` (never part of `src/`, deleted after use, regenerated by hand from `index.html` + the current build's hashed filename whenever needed again) that stubs `window.chrome.storage.local` (a fake `authToken`) and `window.fetch` (canned `/api/applications/`+`/api/profile/` responses covering every status) before loading the same compiled `main-*.js`/`styles-*.css` the real extension ships — the actual compiled Angular app runs unmodified against fake data instead of a real server. Not a permanent fixture (`npm run build` wipes `dist/` on every run, so it never survives a rebuild by accident) — just the fastest way to get eyes on real rendered output when a plain empty-state load isn't enough to trust the result.

## Structure
- `dashboard/` — full Angular CLI workspace (`angular.json`, `package.json`, `tsconfig*.json`, `src/`).
- `dashboard/src/app/app.ts`/`app.html`/`app.css` — root component: the sidebar, the `activePage` switch, and all the cross-cutting state (which application's assistant panel is open, etc.) that doesn't belong to any one page.
- `dashboard/src/app/applications-service.ts` — native-TS `chrome.storage.local` CRUD (see above); exposes a `signal<Application[]>` so every consumer re-renders on any mutation.
- `dashboard/src/app/stats-flow/` — the flow diagram (Overview page).
- `dashboard/src/app/application-list/` — table view (Jobs page): inline status change, edit, delete, plus the "Cover Letter"/"Prep Answers" row actions (see "Assistant" below).
- `dashboard/src/app/application-board/` — Kanban board view (Jobs page, the default), drag-and-drop status columns via `@angular/cdk`. Same row actions/outputs as `application-list/`, just card-shaped.
- `dashboard/src/app/application-form/` — add/edit form, same field set as the popup's "Add Manually" tab (Jobs page). No router (`--routing=false`) — `activePage` is just a signal, not a route.

## Working notes
- **There is now a real build step for this one piece.** Chrome loads the unpacked extension straight from disk — there's no server — so any change under `dashboard/src/**` requires `cd dashboard && npm run build` before reloading the extension, or the popup's "Dashboard ↗" button opens stale compiled output.
- **`angular.json`'s `anyComponentStyle` budget raised 4kB/8kB → 8kB/12kB** — the redesign's `app.css` (new theme tokens, stat tiles, view toggle) alone landed at 4.88kB, over the old warning threshold. Same non-issue reasoning as the earlier `initial` bundle-budget bump for `pdfjs-dist`/`mammoth`: this extension loads from local disk, not over a network, so the download-time budgets Angular's defaults are calibrated for don't really apply here either.
- `dashboard/.gitignore` (Angular CLI's default) excludes `/dist` — fine for now since this project isn't a git repo yet, but worth remembering whenever it becomes one: `dist/browser/` is the one build artifact this extension actually needs at runtime (unlike a normal web app's `dist/`, which a server rebuilds/serves fresh), so it can't just be treated as disposable the way `.gitignore` defaults assume.
- `chrome.tabs.create({ url: chrome.runtime.getURL(...) })` from the popup opening the extension's own bundled page doesn't need a `web_accessible_resources` manifest entry — that gate is for web pages/content scripts loading extension resources, not extension-page-to-extension-page navigation from a privileged context.
- Verified the build renders correctly by serving `dashboard/dist/browser/` locally and opening it outside the extension: the whole component tree renders with zero errors, and the *only* failure is the expected one — `chrome.storage` being unavailable outside a real extension context (`TypeError: Cannot read properties of undefined (reading 'local')` in `ApplicationsService.reload()`), confirming everything else (templates, bindings) is structurally sound. This error is expected and unhandled by design — the page is only ever reachable via the popup's own button, never as a real user flow outside the extension.

# Assistant (Resume, Cover Letters, Interview Prep)

## What this is
The dashboard's second AI feature (after the popup's Insights tab), and the first to touch genuinely personal data: upload a resume, get it parsed into a structured, editable candidate profile (experience/education/projects/skills/interests — LinkedIn-style), then use that profile plus a tracked job's details to generate a tailored cover letter and draft answers to interview questions (preset ones like "Tell me about yourself", or any custom question typed in). All local — the resume file itself never leaves the browser, and generation only ever talks to the local Django/Ollama server, same as Insights.

## Scope decisions
- **Job descriptions are now captured** — for two of the four detection paths. `content/detect.js`'s `normalizeJob()` (JSON-LD path) reads `raw.description` when a site's structured data provides one — confirmed present on schwarz-digits.de's posting, for example — and strips it to plain text via a tag-stripping regex, not by assigning it into a detached DOM element's `innerHTML`: that can still trigger side effects (an `<img>` tag begins its request once parsed into any node, even one never attached to the document) even though the fragment is never rendered. `extractIndeedFallback()` also captures one now (`#jobDescriptionText`, via `.innerText` to preserve paragraph breaks) — added after a real user report of a generic-reading letter traced back to this being the one thing that fallback never scraped; see its own bullet under "Indeed fallback" below for the full story, including a second, more general bug (the on-page widget's Save handler silently dropping any captured description, JSON-LD included) found and fixed alongside it. LinkedIn/d.vinci/generic fallbacks still don't capture one automatically — no reliably structured anchor to read there — so `dashboard/src/app/application-form/` has an editable "Job Description" textarea for adding one after the fact.
- **Generation now hard-blocks without a job description — cover letters AND interview answers, not just cover letters.** User feedback: a generated result that never engages with what the specific job actually asks for isn't worth producing at all, degraded-but-generic or not. `assistant/views.py`'s `cover_letter()` and `answer()` views both reject the request with a 400 (`job_description_missing()` in `prompts.py`, same public-helper pattern as `profile_is_empty()`) before ever calling Ollama if `application.jobDescription` is blank — `build_cover_letter_prompt()`'s old `no_jd_note` graceful-degradation branch (write generically instead) was removed entirely along with the trigger, same reasoning as removing `empty_profile_note` for the meta-commentary leak fix. Mirrored client-side by a shared `JobDescriptionGate` component (`dashboard/src/app/job-description-gate/`) used by both `cover-letter-panel.ts` and `interview-answers-panel.ts` — a real shared component, not hand-duplicated markup, since both live in the same Angular build (unlike the popup/content-script boundary elsewhere in this project, there's no reason to duplicate here). It renders a "paste the job description" textarea + Save & Continue in place of the generate UI whenever the panel's working copy of the application has no `jobDescription`, and saves straight onto the record via `ApplicationsService.update()` — no separate edit-form trip needed anymore. The popup's `toggleCoverLetterPanel()` in `popup.js` got the equivalent treatment natively (`renderJobDescriptionGate()`/`renderCoverLetterGenerateForm()`, split out of what used to be one function) since it can't import the Angular component (classic-script boundary, same as always). Note the popup has no interview-answer feature at all (see the Assistant section's Structure list for why), so this only applies to its cover-letter panel.
- **Resume parsing is entirely client-side.** `dashboard/src/app/resume-parsing.ts` extracts plain text from an uploaded `.pdf` (via `pdfjs-dist`) or `.docx` (via `mammoth`) in the browser — the file's bytes never leave the machine. Only the extracted *text* is sent to the local Django server (`POST /api/assistant/parse-resume/`) to be structured by Ollama. `pdfjs-dist`'s worker script (`pdf.worker.min.mjs`) is copied into `dashboard/public/` so it ships as a static asset and resolves under `baseHref: "./"` the same way every other asset does.
- **Cover letters are plain text only** — a result textarea, a Copy button, and a `.txt` download (`Blob` + a temporary `<a download>`, which works normally here since this is a real extension page with full browser capabilities, not a sandboxed context). No document-generation dependency.
- **`assistant` is a separate Django app from `analysis`**, even though both just call Ollama — different concern (candidate-profile content generation vs. job-search stats/insights), and keeping them apart means `analysis` stays exactly as scoped as it already was. Both import `analysis.ollama_client` directly rather than duplicating the Ollama-calling code a third time.
- **`analysis/ollama_client.py` got generalized** to support this reuse — it used to unconditionally force `format: "json"` and hardcode an analysis-specific fallback shape (`summary`/`interview_patterns`/...) on a parse failure, which made it *not* actually reusable despite looking generic. Now `generate(prompt, json_mode=True, temperature=None)`: `json_mode=False` skips the JSON constraint entirely (used for cover letters/answers — forcing JSON on natural-language output produces awkward quoted-string prose instead of clean text) and returns raw text; a JSON parse failure raises `OllamaResponseParseError(raw_text)` instead of guessing a fallback shape, so each app's own view decides what its fallback should look like (`analysis/views.py`'s `except` block was updated to build the exact same fallback shape as before — see its regression test).
- **Candidate profile lives in its own `chrome.storage.local` key (`"profile"`)**, written only from `dashboard/src/app/profile-service.ts` — structured editing (dynamic experience/education/project lists, AI extraction) stays dashboard-only. `popup/storage.js` got a small `getProfile()` **read-only** addition once the popup's own quick-generate action (below) needed to hand a profile to the same endpoint — it just reads the key, it doesn't shape or validate it, so the "one writer" property Profile editing depends on is unchanged.
- **Profile editing uses signals, not the uncontrolled-form pattern** the rest of the dashboard's forms use. AI-extracted experience/education/projects are dynamic lists (add/remove entries), which template-ref reads on submit don't handle well. The concern that motivated avoiding `[(ngModel)]` elsewhere was two-way *binding sugar* specifically, not signals — signal writes are the actual primitive Angular's zoneless change detection is built around, so `profile-view.ts` uses `signal`/`effect` for its editable draft instead, which is the more natural fit here, not a step back from that earlier decision.
- **The "Generate Cover Letter" row action is gated on `status === 'Pending'` and visually highlighted** (`application-list.html`/`.css`) — a filled accent button (`.cover-letter-button`) rather than the plain text-style row actions, since it's the one action most worth nudging the user toward on a job they haven't applied to yet. It disappears once the status moves off `Pending`, since a cover letter isn't useful after the application's already gone out. "Prep Answers" deliberately stays visible at every status, unhighlighted — interview prep matters *more*, not less, once a job reaches `Applied`/`Interview`, so it isn't gated the same way.
- **The popup also has a quick-generate Cover Letter action** (`popup/popup.js`'s `toggleCoverLetterPanel()`), not just the dashboard — same `Pending`-only gating and highlighted button as `application-list.html` above (`.cover-letter-button` in `popup/popup.css`), added directly to each `app-card`'s actions row. It's a second, thinner client of the same `POST /api/assistant/cover-letter/` endpoint (`requestCoverLetter()` in `popup.js` duplicates `assistant-api.ts`'s request/error shape rather than importing it, since that file is part of the dashboard's TypeScript build and `popup.js` is a plain, buildless ES module) — no interview-answer generation in the popup, since that wasn't asked for and the popup's 340px width/460px scroll area is a worse fit for a second generation flow than the dashboard already is. Clicking the button toggles an inline panel under the card (notes textarea → Generate → result), one open at a time across the list (closing any other card's panel first) to avoid cluttering the small popup. **"Save" persists the letter onto the record itself** (`updateApplication(app.id, { coverLetter })`, a new optional `Application` field — same schemaless-array reasoning as the rest of the "Data Model" section) rather than triggering a `.txt` download — simplest thing that lets the user come back to a previously generated letter (reopening the panel pre-fills the result box from `app.coverLetter` if set) without regenerating, and matches what was actually asked for (save or copy, not a download). "Copy" uses `navigator.clipboard.writeText`, same as the dashboard's panel.
- **`Profile` gained `fullName`/`email`/`phone`.** Added specifically so generated cover letters can be signed and addressed properly (a formal letter with no name on it reads as obviously AI-generated) — extracted by `parse_resume` (schema hint in `RESUME_SCHEMA_HINT` now asks for them alongside experience/skills/etc.) and editable at the top of `profile-view.html`, same "correctable manually, AI extraction won't be perfect" pattern as the rest of the profile.
- **`Profile` also gained `languages`/`certifications`** (both `string[]`, same comma-separated-tag editing pattern as `skills`/`interests` — a certification's issuer/year, if any, is just part of the tag's text rather than its own structured sub-field, since these are typically one short phrase each and didn't warrant `experience`/`education`-style entry cards). Extracted by `parse_resume` alongside everything else, and used in cover-letter/answer matching via `_format_profile()` the same as any other section — a job asking for a specific language or certification can now actually be matched against real profile data instead of silently having nothing to match against.
- **`profile-view.html` can show the exact raw extracted resume text, not just the AI-summarized structured fields.** User feedback: after the "resume text is now always available to generation" fix (below), the natural next ask was to actually let the user *see* what was extracted, not just trust it happened. A "view exact extracted text" toggle next to the resume filename reveals a read-only `<textarea>` of `profile.resumeText` verbatim — the same text `_format_profile()` already sends to generation, so what's shown here is exactly what generation sees, not a separate, possibly-stale copy.
- **`parse_resume`'s Ollama call now passes `temperature=0.2`**, same as `cover_letter`/`answer` already did — it was the one assistant-app generation call left at Ollama's default (~0.8). User report: a real multi-job resume's raw text (visible via the viewer above) looked complete, but the structured form fields it produced looked sparse by comparison — most likely explained by that profile having been parsed before this session's extraction-prompt improvements (the "don't compress descriptions" fix and the `fullName`/`email`/`phone`/`languages`/`certifications` fields didn't exist in earlier parses, so an old saved profile would look thin next to what the current prompt now extracts) — but a resume with several jobs and dozens of skills is also a lot to extract faithfully in one pass, and a high default temperature is the wrong tool for a task that should be thorough and consistent rather than varied. Confirmed via repeated live runs against a real 4-job, 30-skill resume: extraction is complete and consistent at `temperature=0.2`. If a user reports a sparse-looking profile from an older upload, the fix is simply re-uploading the resume so it re-parses with the current prompt.
- **Cover letter generation is requirement-matching, not just profile-restating.** User feedback on the first version: it read as a "very general" letter that used the candidate's background but ignored what the specific job actually asked for. `build_cover_letter_prompt` in `assistant/prompts.py` now explicitly instructs the model to read the job description, identify its 3-5 real requirements, and connect each one to a genuinely matching piece of the profile — and, for a requirement the profile doesn't support, to name the gap honestly and pivot to willingness/ability to learn it (folded into `ANTI_FABRICATION_RULE` itself, with a concrete Terraform example, since a claimed skill the candidate doesn't have is the same failure mode as a fabricated job history, just aimed at requirements instead of experience). Confirmed live against `llama3.1:8b`: this produces letters that name the real requirement, cite a real matching skill/project, and — for an unmet requirement like Terraform — say so plainly and pivot to eagerness to learn it, instead of ignoring the requirement or vaguely implying the candidate already has it.
- **The formal letter header/salutation/signature are assembled in Python (`format_cover_letter()` in `assistant/prompts.py`), never written by the model.** The first version asked the model to write the whole letter, header included, with an instruction to omit the name/contact block entirely when the profile has none. Confirmed live: instead of omitting it, `llama3.1:8b` **fabricated a complete fake identity** — a plausible name plus an invented email and phone number, not a placeholder. That's strictly worse than the employer/metric fabrication `ANTI_FABRICATION_RULE` already targets (a fake name on a letter that might actually get sent is actively harmful), and no amount of rewording the instruction fixed it reliably. So the model is now asked for the body paragraphs only (explicitly told not to write a salutation or signature); `assistant/views.py`'s `cover_letter` view then calls `format_cover_letter(profile, application, body)` to assemble the real name/contact (only if present in the profile — omitted, not placeholder-filled, when absent), today's date, a salutation using the real company name, the generated body, and a "Sincerely," signed with the real name (or unsigned if none) — the same "don't ask the LLM for what Python can compute exactly" principle `analysis/stats.py` already applies to counts/rates, just extended to identity data. `format_cover_letter()` also runs a narrow `_strip_meta_preamble()` safety net (strips a single leading line like "Here is the cover letter body:" if the model adds one anyway, despite being told not to) — confirmed live that the instruction alone doesn't always hold.

## Known limitation: fabrication risk in generated text
Confirmed live while building this, not theoretical: with an empty or thin candidate profile, the model (`llama3.1:8b`) readily **invents** a plausible-sounding but entirely fabricated employer, project, or specific metric ("reduced query times by 30%") rather than writing more honestly in general terms — a real risk if a generated letter gets submitted to an actual employer without being reviewed first. Mitigated two ways, neither of which is a complete fix:
1. `assistant/prompts.py`'s `ANTI_FABRICATION_RULE` is stated at the very start of the prompt (primacy), repeated at the end (recency), and explicitly forbids describing any unstated specific job/project/accomplishment — confirmed this needed to be this forceful, since a single, softer, middle-of-prompt instruction was tried first and the model still fabricated a "previous project" on retest.
2. `assistant/views.py`'s `cover_letter`/`answer` views call `ollama_client.generate(..., temperature=0.3)` — lower temperature to make the model stick closer to the given profile rather than embellishing.

Together these produced a clear, confirmed improvement (retested live) but not a guarantee — small local models don't reliably follow negative instructions, and **always re-read generated text before actually sending it** remains true regardless of the changes below.

**Update: cover letters now hard-block on an empty profile; answers still don't.** The paragraph above originally argued a UI-level hard block wasn't worth it — a general, honest letter grounded in just the job description was treated as a legitimate degraded case. User feedback reversed that specifically for cover letters, after a real generation confirmed a *worse* failure mode than plain genericness: with an empty profile, `llama3.1:8b` sometimes narrated its own reasoning straight into the output as literal leaked text, e.g. *"Since the candidate profile is empty, I will write a letter that focuses on genuine interest in the role and company, without making any assumptions or inventing specific details."* appearing as the letter's first line. An empty-profile cover letter is now blocked outright rather than attempted:
- `assistant/prompts.py`'s `profile_is_empty(profile)` (public — previously a private `_profile_is_empty()` used only inside this file) is checked by `assistant/views.py`'s `cover_letter()` view *before* calling Ollama at all — a 400 with a message pointing the user at the Profile page, never a generation attempt. `build_cover_letter_prompt()` can now assume there's always something real to draw on, so its `empty_profile_note` instruction (the thing the model was narrating back) was removed entirely — removing the trigger, not just telling the model to hide it better.
- `build_answer_prompt()` (interview-answer generation) deliberately keeps allowing an empty profile — a candidate genuinely can and does answer "tell me about yourself" honestly in general terms with nothing on file, which doesn't carry the same "submitted to an employer as-is" risk a cover letter does. Its own `empty_profile_note` was reworded to explicitly forbid narrating the emptiness ("never mention that the profile is empty... a real person answering out loud would never say that") rather than removed, since the empty-profile case here is still real and intentional.
- **Client-side mirrors of the block**, so the message shows immediately instead of only after a round-trip 400: `dashboard/src/app/profile-service.ts`'s `isProfileEmpty()` and `popup/storage.js`'s `isProfileEmpty()` — both hand-duplicated copies of the same field-presence check as `profile_is_empty()` (no shared module across the Python/TS/classic-script boundaries, same situation as every other cross-context duplication in this project). The dashboard's `cover-letter-panel.ts` checks this before rendering the notes/Generate UI at all, showing a "Set Up Profile" message + button (wired to `app.ts`'s `goToProfileFromAssistant()`, which switches `activePage` to `'profile'`) instead. The popup's `toggleCoverLetterPanel()` in `popup.js` does the same, `await getProfile()`-ing before building any panel markup, showing an "Open Dashboard" button instead (the popup has no Profile page of its own — Profile only exists in the dashboard, see "Assistant"'s Structure list).
- **`_strip_meta_preamble()` was broadened** as defense-in-depth on top of removing the trigger — the original heuristic only caught a short label-shaped first line (ends with `:`, or starts with "here is"/"sure,"/etc.), which the actual leaked sentence above matched none of (it ends with a period, starts with "Since"). A second pass now checks the first paragraph's opening sentence against content-based signals (`_META_COMMENTARY_SIGNALS` — phrases like "candidate profile", "i will write", "without making any assumptions") rather than shape, and drops just that sentence (or the whole first paragraph, if the leak was the entire thing) while preserving the rest. Confirmed against the exact reported leak text in a standalone check before relying on it.
- **Post-generation review is now mandatory**, not just an implicit "you should probably reread this": both `cover-letter-panel.ts`/`.html` (dashboard) and `toggleCoverLetterPanel()` (popup) show a "⚠️ AI-generated text can contain mistakes" warning plus an "I've read this and confirm it's accurate" checkbox once a letter exists, and Copy/Download stay disabled until it's checked. Generating/regenerating resets the checkbox (a fresh letter needs fresh review), but a letter that was already saved from an earlier session opens pre-checked — re-litigating a review the user already did the last time they had the panel open would just be friction, not a safety improvement.

Two more instances of the same underlying limitation, found and mitigated later (see the requirement-matching/header bullets above for the fixes):
- **Fake identity, not a placeholder.** With no name on file, the model didn't honor "omit the header" — it invented a complete fake name/email/phone instead. This is why the header is no longer left to the model at all (`format_cover_letter()`); prompt wording alone was tried first and did not hold.
- **Cross-attributing a user's own note.** Given a note like "I'm currently learning Kubernetes in my spare time" alongside a job description that separately asked for Terraform, one generation applied the note's "experimenting in my spare time" phrasing to Terraform instead of Kubernetes — a subtle real-detail-used-in-the-wrong-place error, not an invented one. `notes_block` now explicitly says not to repurpose a note for a different requirement than the one it actually names; confirmed improved on retest, but — same caveat as everywhere else in this section — always re-read before sending, this class of error is easy to skim past since every individual fact in the letter is technically real.
- **Structured resume extraction can quietly compress away real detail.** User-reported: a resume that specifically said testing work was done at a named employer got extracted into `experience[].description` in a way that lost that specificity — the cover letter then only connected generic language skills to a testing role instead of citing the actual testing experience, reading as a shallow "these skills make me a candidate" leap rather than a real match. `_format_profile()` now always appends the full original `resumeText` (already saved on the profile by `resume-upload.ts`, just never previously read by the generation prompts) as an explicit "fuller, more authoritative source" alongside the structured summary, so a lossy structured field no longer means the detail is unreachable by generation. `RESUME_SCHEMA_HINT`'s experience `description` field was also reworded to stop asking for a compressed "1-3 sentences" and instead keep specific tools/methodologies/types of work as written. Confirmed on retest: the same resume now round-trips the testing detail intact, and the resulting letter cites it specifically instead of guessing a connection between unrelated skills and the job.
- **Cliché sentence shapes survive being told not to use them — they just get reworded.** Told explicitly not to write "I'm excited about the prospect of working in a complex technical environment," `llama3.1:8b` produced "I'm excited about the prospect of bringing my experience to bear on Delta Systems' complex technical environment" on the next attempt — dodging the literal string while keeping the exact same clichéd sentence shape. Escalated the instruction twice (a named specific example, then an explicit list of banned *sentence shapes* rather than exact wordings, e.g. "I'm [excited/thrilled/eager] about the prospect of ___ — no matter what fills the blank") and it still recurred in some form on the next generation. Treat this as a real, current ceiling of an 8B local model on stylistic instructions specifically (as opposed to the factual/identity fixes above, which held reliably once moved out of the model's hands entirely) — **always skim the opening and closing sentences of a generated letter and rewrite by hand if they read like a template**, this is the one class of issue in this file that prompt engineering alone hasn't fully closed. A larger local model or a cloud provider (see "Future Phases") would be the next lever to pull if this matters more than the effort already spent here justifies.
- **Inferring an entire false technical identity from the job title — the worst fabrication found yet, fixed with a computed whitelist instead of more prompt wording.** User-reported, confirmed real: applying to a job titled "SAP Entwickler" (SAP Developer) against a profile showing only Java/Python/JavaScript/Spring Boot/React (no SAP or ABAP anywhere), `llama3.1:8b` wrote "As a seasoned ABAP/4 and ABAP OO developer, I have a proven track record..." and "I have developed a strong foundation in ABAP/4 and ABAP OO programming languages" — a complete, confident, specific fabrication of expertise, inferred purely from the job title matching a technology stack. This is qualitatively worse than the genericness `ANTI_FABRICATION_RULE` was originally written against: it's not vague filler, it's a false, specific, checkable claim. The abstract instruction ("don't claim a skill the profile doesn't show") wasn't enough on its own to stop it — the model needed something to mechanically check itself against, not just a principle to reason from. Fixed with a deterministic guardrail, same "don't ask the LLM for what Python can compute exactly" principle as `format_cover_letter()`'s header assembly: `_extract_known_skills(profile)` in `prompts.py` collects the candidate's actual `skills`/`languages`/`certifications`/`projects[].technologies` into a de-duped list (never asking the LLM to identify this itself), and `_skill_whitelist_block()` turns it into an explicit "KNOWN, VERIFIED SKILLS — this is the ONLY set you may say or imply the candidate has expertise in: {list}" block, inserted right after `ANTI_FABRICATION_RULE` at the very top of both the cover-letter and answer prompts (primacy, same reasoning as `ANTI_FABRICATION_RULE`'s own placement) — see `skill_whitelist_template` in `prompts.json`. The template also names the exact real ABAP failure as a permanent concrete counter-example (the same "escalate with the literal observed bad output" pattern that worked for the cliché-sentence-shapes fix above), rather than a generic warning. Covered by a regression test (`test_prompt_includes_computed_skill_whitelist_excluding_job_title_tech` in `assistant/tests.py`) confirming the computed whitelist reaches the actual prompt text and correctly excludes ABAP/SAP for this exact profile/job-title combination — that test can only confirm the guardrail is wired in, not that a live model never fabricates again; same "always re-read before sending" caveat as every other entry in this section.

## Structure
- `server/assistant/` — `views.py` (`POST /api/assistant/{parse-resume,cover-letter,answer}/`), `prompts.py` (the three prompt builders + `ANTI_FABRICATION_RULE`, plus `format_cover_letter()`/`_strip_meta_preamble()` — the deterministic letter-assembly step described above), `tests.py` (mocked-Ollama, same approach as `analysis/tests.py`). Mounted via `path('api/assistant/', include('assistant.urls'))` in `jobtracker_server/urls.py`.
- **Prompts are externalized to JSON, not hardcoded in Python.** `server/assistant/prompts.json` holds every actual piece of prompt wording used in this file — `RESUME_SCHEMA_HINT`, `ANTI_FABRICATION_RULE`, the cover-letter body template, the answer template, the notes/no-JD/empty-profile note snippets, and the `_strip_meta_preamble()` safety-net lists (`preamble_prefixes`, `meta_commentary_signals`). `prompts.py` loads the file once at import time (`pathlib.Path(__file__).resolve().parent / "prompts.json"`) and does only two things with it: data-shaping (`_format_profile`/`_format_application`, turning a profile/application dict into prompt text) and `str.format()` substitution into each template's named `{placeholder}` slots — tuning a rule's wording, an example, or a banned phrase is now a JSON edit, never a Python diff. `server/analysis/prompts.json`/`prompts.py` follow the identical pattern for the Insights prompt. Substituted values (profile text, job descriptions, user notes — all untrusted, user-supplied) are safe to contain literal `{`/`}` characters: `str.format()` only parses the *template* string for placeholders, never re-scans the values inserted into it. Keep a template's `{placeholder}` names in the JSON in sync with what `prompts.py` passes to `.format()` by hand — a mismatch raises a `KeyError` at generation time (loud, not a silent wrong-prompt bug).
- `dashboard/src/app/profile-service.ts` — the `Profile` type and `chrome.storage.local` CRUD for it.
- `dashboard/src/app/resume-parsing.ts` — client-side PDF/DOCX → text extraction.
- `dashboard/src/app/assistant-api.ts` — shared `fetch` wrapper for the three Django endpoints (same error-message pattern as the Insights tab).
- `dashboard/src/app/resume-upload/`, `profile-view/` — upload + editable structured-profile display, in the dashboard's new "Profile" section.
- `dashboard/src/app/cover-letter-panel/`, `interview-answers-panel/` — opened from new "Cover Letter"/"Prep Answers" buttons on each row in `application-list.ts`.
- `dashboard/src/app/job-description-gate/` — shared "paste the job description first" component used by both panels above; see the job-description hard-block bullet under Scope decisions.
- `popup/storage.js`'s `getProfile()` — read-only access to the `"profile"` key, added for the popup's own quick-generate action below; `popup/popup.js`'s `requestCoverLetter()`/`toggleCoverLetterPanel()` — the popup's thinner equivalent of `assistant-api.ts`/`cover-letter-panel.ts`. Both `storage.js` and `profile-service.ts` also export an `isProfileEmpty()` — see the empty-profile-block update above.

# Future Phases: AI Career Intelligence

The extension is not merely a job tracker. Its long-term purpose is to become an AI-powered career intelligence assistant that helps users understand and improve their job search.

## Guiding Principles

* AI features are optional and user-controlled.
* The user owns all of their data.
* AI analysis should be explainable and based on evidence from the user's application history.
* Personal information is only analyzed with explicit user consent.
* Support both local LLMs (via Ollama or LM Studio) and cloud models (OpenAI, Anthropic, Google Gemini) through a provider abstraction.

## Data Collection

For each application, store:

* Job title
* Company
* Industry
* Department
* Location
* Country
* Employment type
* Seniority level
* Salary (if available)
* ATS platform
* Job ID
* Job URL
* Application date
* Job posting date (if available)
* Days between posting and application
* Resume version used
* Cover letter version used
* Skills extracted from the job description
* Technologies mentioned
* Experience required
* Education requirements
* Employment status (Applied, Interview, Offer, Rejected, etc.)
* Timeline of status changes
* Notes
* Full job description snapshot (optional)
* AI-generated structured metadata

## User Profile

Allow the user to optionally upload:

* Resume(s)
* CV(s)
* Cover letters
* Portfolio
* LinkedIn profile export
* GitHub profile
* Skills
* Certifications
* Work history
* Preferred countries
* Preferred industries

The system should create a structured candidate profile that can be updated over time.

## AI Resume Analysis

The AI should analyze:

* Resume strengths
* Missing keywords
* Missing technical skills
* Missing soft skills
* Resume readability
* ATS compatibility
* Experience gaps
* Overused phrases
* Weak bullet points
* Missing measurable achievements

The AI should generate actionable recommendations rather than generic advice.

## Job Description Analysis

For every saved application, extract:

* Required skills
* Preferred skills
* Programming languages
* Frameworks
* Years of experience
* Certifications
* Industry
* Seniority level
* Company size
* Remote / Hybrid / On-site
* Salary range
* Responsibilities

Store this in structured JSON so it can be queried later.

## Career Analytics Dashboard

Generate interactive dashboards showing:

### Application Overview

* Total applications
* Active applications
* Interviews
* Offers
* Rejections
* Withdrawn
* Ghosted
* Response rate
* Interview rate
* Offer rate

### Timeline Analysis

Visualize applications, interviews, offers, and rejections over time. Identify trends and seasonality.

### Posting Speed Analysis

Calculate:

* Average days between job posting and application
* Median response time
* Success rate based on application speed

Example insight: "Applications submitted within 24 hours have a 28% interview rate. Applications submitted after 10 days rarely receive responses."

### Industry Analysis

Show interview/offer/rejection rate by industry.

Example insight: "You receive interviews from Manufacturing companies twice as often as FinTech companies."

### Company Analysis

Rank companies by interview success, offer success, response speed, and average hiring duration.

### ATS Analysis

Compare success across recruitment platforms: LinkedIn, Greenhouse, Workday, Lever, SuccessFactors, Ashby, Taleo, SmartRecruiters.

Example: "You receive more interview invitations from Greenhouse-hosted jobs than Workday-hosted jobs."

### Skills Analysis

Extract skills from every job description and compare them against the user's profile. Generate most-requested skills, missing skills, skills already possessed, and emerging trends.

Example: "You already know React, but 72% of rejected jobs also requested Docker and Kubernetes."

### Resume Version Analysis

If users upload multiple resume versions, track interview/offer/rejection rate per version.

Example: "Resume Version 3 increased interview rate by 18% compared with Version 2."

### Cover Letter Analysis

Compare performance of different cover letter templates. Recommend which template performs best for different industries.

### Geographic Analysis

Show countries, cities, and Remote vs Hybrid vs On-site performance.

Example: "You receive significantly more interviews from remote positions than hybrid positions."

### Role Analysis

Group applications by role (Software Engineer, Data Engineer, ML Engineer, Backend Engineer, DevOps, AI Engineer) and calculate success rates for each.

### Salary Analysis

Estimate average advertised salary, interview rate by salary range, and offer rate by salary range.

## AI Insights

Instead of only displaying charts, generate personalized insights, e.g.:

* "You have a 41% interview rate for Backend Engineer positions but only 8% for Frontend roles."
* "Your strongest industry is Industrial Automation."
* "Applications submitted within two days of posting perform much better."
* "Companies requesting Kubernetes are much more likely to invite you to interview."
* "You frequently reach technical interviews but rarely receive offers. Practicing interview performance may have the highest impact."

## Weekly AI Reports

Generate a weekly summary that includes: new applications, status changes, interviews scheduled, new offers, rejections, success trends, resume recommendations, skill recommendations, industry recommendations.

## Career Coach

The AI should act as a career advisor, e.g.:

* "Focus on Backend Engineer roles."
* "Reduce applications to Frontend positions."
* "Learn Docker before applying to Platform Engineering roles."
* "Your profile aligns strongly with Manufacturing and Automotive companies."
* "Applications older than 30 days with no response are likely inactive."

## AI Architecture

Create a provider abstraction for LLMs. Support OpenAI, Anthropic Claude, Google Gemini, Ollama (local), LM Studio, and future providers. Never hardcode a specific model.

Use a common interface:

* `summarize()`
* `analyzeResume()`
* `analyzeJobDescription()`
* `compareResumeToJob()`
* `generateInsights()`
* `createWeeklyReport()`
* `recommendSkills()`

## Privacy

Users choose whether AI runs fully local, cloud-based, or hybrid. No personal information should leave the user's device without explicit consent. Clearly indicate which provider is being used for each analysis.
